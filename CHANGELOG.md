### Added

- **弹窗补一句「这一页还没收到最新配置」**：改完规则要推一份新配置给已打开的页面（复杂规则靠它实时生效），而**推送失败过去是被静默丢掉的**——`Promise.allSettled` 的结果没人读，注释写的就是「静默忽略即可」。于是「我改了规则，这个页没反应」只剩两种解释：怀疑自己没改对，或者回去逐条排查规则，而真实原因常常与规则无关——页面是在扩展安装、更新或重载**之前**就打开的（那个文档里根本没有内容脚本），或者该站点被禁用了扩展；前者的解法是刷新这一页，后者还得先在 Chrome 的扩展菜单里为该站点重新开启，而界面上没有任何线索指向它们。现在桥接层对 `UPDATE_PROXY_CONFIG` **同步回执**（不作答时 Chrome 那边「有监听器但不回话」与「压根没有内容脚本」无从区分，那句提醒就会变成随机噪声；回执只说「收到了」，不带任何规则内容），后台按标签页记一笔只含**已知失败**的账：接住即清账、拒收即记档，而且**逐页各记各的**——一次广播要等最慢的那一页回执，把记账留到全部落定再统一做，中途刷新那一页刚留下的清账就会被一笔迟到的标记盖回去，成句假警告；内容脚本自己拉到配置（`GET_PROXY_CONFIG`）时同样当场销账。这笔账全在内存（`entrypoints/background/configSyncState.ts`，上限 200 个标签页——一次扩展重载能让**所有**已打开的 http(s) 页同时处于未同步状态，收得像拦截器自报那样只留 10 个，就会把大部分警告静默丢掉），`tabs.onRemoved` 与整页导航到 `loading` 时清账，SW 回收即归零，**不落 `storage`、不参与任何判定**。参与记账的只有 http(s) 且 `status === 'complete'` 的页面：`chrome://`、商店页与扩展页永远收不到推送、刷新也救不回来，给它们记一笔就是句假警告；正在加载的文档处在「新文档自己会去拉配置」的窗口期，那时记同样是误报。清账时机刻意**只认 `loading`、不认 `complete`**——需要这句话的场景，页面恰恰早已 `complete`。记账方向也刻意是「只记已知的问题」：没有这笔账就算已同步，否则「不知道」会被画成「有问题」。弹窗因此多出一行「此页尚未收到最新配置，刷新这一页通常可恢复」，悬停点名上述两种原因与各自的修法，且只在总开关开启、本页可代理、这次**确实取到了**账时才出现（取不到就不显示，而不是显示「同步正常」）。新增的读取消息 `GET_CONFIG_SYNC` 与 `GET_DNR_STATS`、`GET_INTERCEPTOR_STATS` 同档**不设** `isTrustedSender` 门禁，回包只有一个布尔值。一处已知边界：这笔账是**标签页**粒度而非 frame 粒度——不带 `frameId` 的 `tabs.sendMessage` 一次发给全部 frame，回执只证明「有 frame 接住了」，所以顶层框架已同步、某个 iframe 仍跑旧配置时这句话不会出现；做到 frame 粒度需要 `webNavigation` 级别的定位，刻意不为它加权限。`tests/configSyncState.test.ts` 覆盖账本与逐标签页记账（含「`complete` 不清账」「一个标签页失败不牵连其他」「非 http 页不参与」），`tests/messageRouter.test.ts` 钉住它留在门禁外、页面来源照常可读、读取不改账。
  **The popup now says when a page never received the latest rules.** Editing a rule pushes the new config to open tabs (that's how complex rules take effect live), and **failed pushes were being thrown away** — nobody read the `Promise.allSettled` results, and the comment literally said to ignore them silently. "I changed the rule and this page didn't react" therefore had two remaining explanations: you mistyped something, or you go audit the rules one by one — when the real cause is usually nothing of the sort. The page predates the install, update or reload of the extension (so that document has no content script at all), or the extension is disabled for the site — a reload fixes the first, while the second has to be re-enabled for that site from Chrome's extension menu first — and nothing on screen pointed at either. The bridge now **acks `UPDATE_PROXY_CONFIG` synchronously** (without an answer, Chrome cannot tell "a listener exists but never responds" from "there is no content script", and the warning would be noise; the ack says only "received" and carries no rule content), and the background keeps a per-tab ledger of **known failures only**: received clears it, refusal records it, and every tab settles its own entry as its own reply arrives rather than once the whole broadcast finishes — one slow page otherwise drags the accounting past a reload that already cleared that tab, resurrecting the failure as a fabricated warning, while a content script that fetches the config itself (`GET_PROXY_CONFIG`) settles its entry on the spot. That ledger lives in memory (`entrypoints/background/configSyncState.ts`, up to 200 tabs — one extension reload can leave _every_ open http(s) page unsynced, and a cap like the interceptor's 10 would silently drop most of the warnings), cleared on `tabs.onRemoved` and when a tab navigates to `loading`, zeroed again when the worker is recycled; nothing goes to `storage` and nothing feeds a decision. Only http(s) tabs at `status === 'complete'` take part: `chrome://`, the web store and extension pages can never receive a push and a reload will not help, so marking them would be a fabricated warning, while a document still loading is exactly the window where it pulls the config itself, so marking it would be a false positive too. The clearing deliberately watches `loading` and **not** `complete`, because in the case that needs this sentence the page is already complete. The polarity is likewise "known failures only" — no entry means synced, so "unknown" is never drawn as "broken". The popup gains one line, "This page has not received the latest rules — reloading it usually fixes it", whose tooltip names the two causes and their respective fixes; it appears only with the switch on, this page proxyable, and the ledger actually read this time (no reading means no line, rather than a line saying all is well). The new `GET_CONFIG_SYNC` read sits in the same bracket as `GET_DNR_STATS` and `GET_INTERCEPTOR_STATS` and is **not** gated by `isTrustedSender`; its reply is a single boolean. One accepted boundary: the ledger is per-tab, not per-frame — `tabs.sendMessage` without a `frameId` broadcasts to every frame and the promise only proves one of them caught it, so a page whose top frame is current while an iframe still runs the old rules shows no warning; frame-level precision would need `webNavigation`, and no permission is added for it. `tests/configSyncState.test.ts` covers the ledger and the per-tab accounting (including "complete does not clear", "one failing tab does not taint the others", "non-http pages take no part"), and `tests/messageRouter.test.ts` holds that it stays outside the gate, answers page-origin senders, and never mutates the ledger while reading.
- **弹窗多一行「页面自报」的拦截活动**：复杂规则的请求要经页面里的拦截器交给后台代发，而此前这条链路只在两个出口留痕——控制台一行日志，和「经扩展请求」那个数。于是最常见的两种失败读起来完全一样：一次都没拦到（规则没匹配、拦截器没注入、页面根本不发这类请求），与这一页本来就没有可代理的请求，弹窗上都是「经扩展 0」；而请求被回退成原生（非字符串 body、同步 XHR、代理异常）或代发超时，用户在界面上看不到任何痕迹，只觉得「代理时好时坏」。现在拦截器在四个既有时机上各记一笔（命中规则之后、把请求交给后台之后、回退原生处、超时回调里，调用点共 8 处，因为 fetch 与 XHR 各有命中与回退），攒出四个数（拦到 / 交给后台 / 回退为原生 / 超时），节流发给桥接层再转交后台按标签页存住（首帧立刻报、之后每 10 笔或每秒一次并补一笔尾报），弹窗数据行下方按需显示一句话，有读数时悬停展开四个数与采信时刻（并点名同一请求可同时计入多项、四个数不能相加）。四个数**只在内存里**（`entrypoints/background/interceptorStats.ts`，最多 10 个标签页、按最近写入序逐出且弹窗读取不刷新位置，`tabs.onRemoved` 与文档重新加载时清空），不落 `storage`、不进日志、不改任何判定，所以拦截器的控制流与 fallback 行为一个字都没动（计数处不加 `try/catch`、不引入分支）。读到的自报数会与后台自己数的代发次数交叉校验：低于基线的整包拒收，界面于是维持上一次被采信的读数（从没采信过时才说「没有可采信读数」），绝不画出包内自相矛盾、或低于后台自己数到的代发数的包（与基线自洽的假数仍会画出，所以措辞永远写「页面自报」）。五种状态各占一句话，优先级是回退 > 超时 > 正常（一句话只放得下最该先知道的那件事，其余的数在悬停里）——「还没回报任何被拦截的请求」「本页已向扩展发出 N 个代发请求但无可采信读数」「拦到 N 个其中 M 个回退为原生」「拦到 N 个其中 M 个交给后台后没等到响应」「拦到 N 个其中 M 个已交给扩展代发」，「不知道」与「没有」绝不合并成一句，「未注入」也绝不说成「代理未生效」，有请求超时也绝不说成「一切正常」。新增的两个消息（页面→后台的上报、弹窗→后台的读取）都刻意**不设** `isTrustedSender` 门禁：前者必须由内容脚本发出，加了门禁代理当场失效；后者与 `GET_DNR_STATS` 同档，回包只有六个整数（四个计数，加上采信时刻与后台自己数的代发基线）。WebSocket 握手不参与计数——长连接的能力面与 HTTP 不同，混进来只会让「拦到」这个词失去意义。
  **The popup gains a "page-reported" line about what the interceptor actually did.** A complex rule's request has to be caught by the in-page interceptor and handed to the background, and until now that path left exactly two traces: a console line, and the "via the extension" counter. The two most common failures therefore read identically — nothing intercepted (the rule didn't match, the interceptor never injected, the page simply makes no such requests) and this page has nothing proxyable to begin with — both rendering as "extension: 0", while a request that fell back to native (non-string body, synchronous XHR, an exception in the proxy) or timed out left no visible mark at all, which is what makes the proxy feel intermittent. The interceptor now bumps four counters at four moments that already existed (after a rule matches, after the request is handed over, at the native fallback, in the timeout callback) — eight call sites, since fetch and XHR each have their own match and fallback — giving intercepted / handed over / fell back / timed out, reporting them to the bridge and then to the background on a throttle (immediately, then every 10 requests or every second, plus one trailing report). The popup shows a sentence under its data row when it has something to say, and hovering that sentence while a reading exists expands all four counters plus the moment the report was accepted, with a note that one request can count in more than one of them so they never add up. The four numbers live **in memory only** (`entrypoints/background/interceptorStats.ts`, at most 10 tabs, evicted in last-write order and a popup read does not refresh that position, cleared on `tabs.onRemoved` and on document reload) — nothing touches `storage`, nothing reaches the logs, nothing feeds a decision, and the interceptor's control flow and fallback behaviour are unchanged to the letter (no `try/catch`, no new branch at the counting sites). An accepted report is cross-checked against the background's own proxied count: anything below that baseline is refused outright, so the line keeps the last reading that was accepted (only a tab that never had one says there is no trustworthy reading) and a packet that contradicts itself or sits below the background's own proxied count is never drawn (a self-consistent forgery still is, which is why the wording always says 'page-reported'). Each of the five states gets its own sentence, ordered fallback > timeout > healthy because one line can only carry the thing you most need to know first and the rest lives in the tooltip — no report from this tab yet / this page sent N proxy requests but has no accepted reading / intercepted N of which M fell back to native / intercepted N of which M got no response after being proxied / intercepted N of which M were handed to the extension — so "unknown" and "none" never collapse into one phrase, "not injected" never becomes "the proxy is off", and a page whose requests all timed out is never drawn as "all clear". Neither new message (the page's report, the popup's read) is gated by `isTrustedSender`: the first must come from a content script, where a gate would break proxying on the spot, and the second sits in the same bracket as `GET_DNR_STATS` with a reply of six integers (the four counters, plus the acceptance timestamp and the background's own proxied baseline). WebSocket handshakes are deliberately not counted — long connections have a different capability surface, and folding them in would only drain "intercepted" of meaning.
- **导入前先预览，整套替换都能回退**：合并导入的判据是「规则名 + 匹配模式」，所以一条只改了目标地址的同名规则在合并语义下是**新增**而不是更新——这一点此前只有导完再回头看才知道，而「导入完成」的提示历来只有一个笼统的条数。现在导入弹窗在真正写入之前多一步显式的**预览**：预计新增几条、哪些现有规则会顶掉文件里的同名同模式条目、文件内部自身重复哪些，超限的文件在预览阶段就点名。预览与实际写入调用的是同一个 `deduplicateRules`（`utils/importPlan.ts` ＋ `utils/ruleConflicts.ts` 的 `ruleMergeKey`），所以两处的数不会互相打脸；合并必须在存储锁内重算，因此新增条数与超限判定这两句始终说「预计」。写入之后另报一份真实结果（新增 / 保留 / 因非法被丢弃）。配套的三处边界：导出文件开始携带 `schemaVersion`，比当前版本更高的文件给出专属拒绝文案（旧文件照常读取，只拒新不拒旧）；**配置恢复点**在覆盖导入、加载环境快照、真正删掉东西的批量删除这三类整套替换之前先把被替换掉的那份规则集存下（`STORAGE_KEYS.CONFIG_HISTORY`，最近 5 份、合计约 100 万字符预算内、尽力写入——读不到旧账、新快照单份越预算、写配额失败这三种情形都只跳过这一份（旧账原样留着），绝不回滚用户的主操作），列在「设置 → 配置恢复点」里一键回退，回退之前同样先留一条 `before-restore`；回退**只换规则集、不动总开关**，恢复到一份含停用规则的配置不会顺手把代理打开，超过 200 条的快照在回退前就被拒绝。因为恢复点里可能是被手改过的规则原文，`GET_CONFIG_HISTORY` 与 `GET_VARIABLES` 同档过 `isTrustedSender`（判据从「回包是凭据」放宽为「页面永远不会问、而回包是凭据或整包本地数据」），而纯计算的 `GET_IMPORT_PLAN` 刻意不设门禁。
  **Preview an import before it writes, and roll back anything that replaced the whole set.** The merge key is rule name + match pattern, so a rule whose target URL alone changed is an **addition**, not an update — until now you learned that only after the import, from a toast that just said how many rules arrived. The import dialog now has an explicit **preview** step before anything is written: how many rules would be added, which existing ones keep their place over the file's same-name same-pattern entries, which entries duplicate each other inside the file, and an early flag when the file is over the cap. Preview and write call the very same `deduplicateRules` (`utils/importPlan.ts` over `ruleMergeKey` in `utils/ruleConflicts.ts`), so the two can never disagree; the write still recomputes inside the storage lock, which is why the added-count and over-cap lines both say "expected". Afterwards the real numbers are reported (added / kept / dropped as invalid). Three boundaries come with it: exports are stamped with `schemaVersion` and a newer-than-this file is rejected with its own message (older files keep working — only newer is refused); **config restore points** store the rule set that a replace-mode import, a profile load, or a batch delete that actually removed something is about to overwrite (`STORAGE_KEYS.CONFIG_HISTORY`, the last 5 inside a ~1M-character budget, written best-effort — a failed history read, a snapshot that alone exceeds the budget or a quota error only skips that one point (the points already stored survive) and never rolls back the operation the user asked for), listed under Settings → Config restore points for one-click rollback, and a rollback stores its own `before-restore` point first. A rollback swaps rules only — it **never touches the global proxy switch**, so restoring a snapshot full of disabled rules does not quietly turn proxying on, and a snapshot over the 200-rule cap is refused before it can be applied. Because a restore point may hold hand-edited rule text, `GET_CONFIG_HISTORY` is gated by `isTrustedSender` alongside `GET_VARIABLES` — the criterion generalises from "its reply is a credential" to "a page would never ask for it, and its reply is credentials or a whole local dataset" — while the pure computation `GET_IMPORT_PLAN` deliberately stays open.
- **凭据变量库：规则里的 token 写成 `{{名称}}`，真值不再跟着规则走**：「分享模式」管住的是导出那一刻，而凭据仍然原样躺在规则里——每次录入都要把真值复制粘贴一遍，规则跟着配置文件在同事间流转，屏幕上打开规则也是明文。现在「设置 → 凭据变量」把真值单独收进 `storage.local` 的 `variables`（上限 50 条；名字法 `[A-Za-z][A-Za-z0-9_.-]{0,63}`；值裁两端空白，因为粘贴的 token 常带换行而 HTTP 本就会折掉它；超长整条丢弃而不是截断——半把 token 比少一把更难查），规则的两个凭据位点——请求头覆盖的值、查询参数覆盖的值——写成 `{{名称}}` 引用它。**展开只发生在后台出站请求组装前**，三处刻意不展开：本地日志记的是未展开形态（`proxiedUrl` 与 `logger` 都不含真值）；下发给页面世界的仍是字面量（桥接层本就不发 `headerOverrides`，而 WS 规则的 `queryOverrides` 由 MAIN world 拼接、那一侧永远读不到表，所以表单直接拒绝「WebSocket 规则 + 查询参数放引用」这种会静默坏掉的配置）；DNR 通道无需展开（这两个位点早已让 `isSimpleRule` 返回 false）。刻意**不递归展开**：一把变量的值里写着另一把的名字也不会被二次解释，否则一个变量就能引用整张表。手改进存储的换行值在展开后仍过头校验并整条拒绝。读写这两张表的消息 `GET_VARIABLES` / `SET_VARIABLES` 都过 `isTrustedSender`——这是第一次给「读取类」消息加 gate，理由写在路由注释里：内容脚本从不读它，不加 gate 等于页面上任意脚本发一条 `postMessage` 就能取走整张密钥表（targetOrigin 挡不住同页脚本）。`SET_VARIABLES` 收到非键值对象时抛错拒写，一次格式错误不等价于清空用户全部凭据。表单保存处拦下引用了未定义变量的规则（变量表拉取失败时**跳过**这项校验，不把保存变成死路）；设置页每把变量标出「被 N 条规则使用」，删除在用变量需二次确认，规则还在引用而表里已没有的名字列成孤儿告警；设置页对变量表是**整表覆盖写**，所以读取失败时不显示空列表，而是点名「读取失败，列表不代表现状」并拦住紧接着的那次覆盖写入——否则一次失焦保存就会抹掉用户已有凭据。日志详情面板的请求/响应头值默认打码（判据与导出脱敏同源，长值留尾 4 位以分辨「是这把而不是那把」），并给一个「显示凭据原值」开关——不落存储、关掉抽屉即收回；同一抽屉的方法筛选从写死的 GET/POST/PUT/DELETE 改为与规则表单同源的 7 个方法，PATCH / OPTIONS / HEAD 此前在列表里看得见却筛不出来。
  **A credential variable store: rules say `{{NAME}}`, the value no longer travels with the rule.** Share mode only guarded the moment of export; the secret was still written into the rule itself, pasted in by hand every time, shipped to whoever received the config file, and rendered as plaintext whenever the rule was open. Real values now live on their own in `storage.local` under `variables` (up to 50; names match `[A-Za-z][A-Za-z0-9_.-]{0,63}`; values are trimmed, since a pasted token usually carries a newline that HTTP would fold off the header value anyway; over-long values are dropped rather than truncated — half a token is harder to diagnose than a missing one), and the two credential slots of a rule — request header override values and query-parameter override values — reference them as `{{NAME}}`. **Expansion happens only in the background, just before the outbound request is assembled**, and it is deliberately absent in three places: the local log keeps the unexpanded form (neither `proxiedUrl` nor `logger` carries the value); the page worlds still see the literal (the bridge never sends `headerOverrides`, and a WebSocket rule's `queryOverrides` are stitched in MAIN world, which can never read the table — so the form refuses "WebSocket rule plus a reference in a query parameter", a configuration that would break silently); and the DNR channel needs no expansion (both slots already make `isSimpleRule` return false). Expansion is deliberately **not recursive**: a value containing another variable's name is not re-resolved, otherwise one variable could reference the whole table. A hand-edited stored value carrying a newline still fails the header check after expansion, and the rule is rejected as a unit. Both messages, `GET_VARIABLES` and `SET_VARIABLES`, pass `isTrustedSender` — the first time a _read_ message is gated, and the reason is in the router's comment: no content script ever reads it, so without the gate any script on a page could take the entire key table with one `postMessage` (targetOrigin does not stop same-page scripts). `SET_VARIABLES` throws on a payload that is not a key-value object instead of writing it: a format error must not equal wiping every credential the user has. Saving a rule that references an undefined variable is refused at the form (the check is **skipped** when the table could not be fetched, so a transient read failure never dead-ends the save button); the settings panel shows "used by N rules" per variable, deleting a used one asks twice, and names still referenced by rules but absent from the table are listed as an orphan warning. The settings panel overwrites the whole table on every save, so a failed read no longer leaves an empty list on screen: it says the list is not the current state and blocks the overwrite that would follow — otherwise one blur-save against that empty list would wipe the credentials the user already had. Request and response header values in the log detail panel are masked by default (the same predicate export sanitisation uses, keeping the last 4 characters so you can tell which token answered), plus a "reveal credential values" switch that is never persisted and resets when the drawer closes; the same drawer's method filter now iterates the shared 7-method list instead of four hard-coded ones, which is why PATCH / OPTIONS / HEAD used to be visible in the list but unfilterable.
- **按规则的「携带 Cookie」开关，默认关闭**：后台通道代发的请求此前从不带目标环境的 Cookie——代理用的 `fetch` 没有设 `credentials`，默认 `same-origin` 对这些跨源请求等于「一个都不带」，需要登录态的接口一律回 401。唯一的绕法是把会话 Cookie 手工抄进「请求头覆盖」，而那正是本扩展劝用户别做的事：凭据从此明文躺在规则里，跟着配置导出流转，还不按环境区分。现在规则表单多一个开关，开启后由扩展以 `credentials: 'include'` 代发，带上的是**你在目标环境**已有的会话（源站的 Cookie 不会跟过去）。三条边界：判据是严格等于 `true`，导入文件里的真值字符串（`"true"`、`1`）一律按未开启处理，不可信输入不得悄悄打开凭据开关；它强制走后台通道（`isSimpleRule` 对它返回 false），因为 DNR 重定向后请求由浏览器直接发出，扩展无从干预其 Cookie；它同属「页面侧从不读取」的字段，桥接层下发前剥掉。规则列表为它立一枚 **C** 徽章，提示语把代价写在明面上——这条规则命中的每个请求都会带上你在目标环境的登录态，只对可信环境启用。
  **A per-rule "send cookies" switch, off by default.** Requests made by the background channel never carried the target environment's cookies: the proxying `fetch` left `credentials` unset, and the `same-origin` default means "none" for these cross-origin requests, so any session-guarded endpoint answered 401. The only workaround was pasting the session cookie into the header overrides, which is precisely what the extension tries to make unnecessary — the credential then lives in the rule in plaintext, travels with every config export, and is not scoped per environment. The rule form now offers a switch, and enabling it makes the extension fetch with `credentials: 'include'`, sending the session you already have _at the target_ (the source site's cookies do not follow). Three boundaries: the test is strict equality with `true`, so truthy strings from imported files (`"true"`, `1`) stay off — untrusted input may not open a credential switch; it forces the rule onto the background channel (`isSimpleRule` returns false), because after a DNR redirect the browser issues the request and the extension cannot touch its cookies; and it is one of the fields the page never reads, so the bridge strips it before broadcasting. The rule list carries a **C** badge for it, and the hint states the cost outright: every request this rule matches will carry your session there, so enable it only for trusted environments.
- **导出配置默认走「分享模式」，凭据不再跟着文件走**：导出的 JSON 就是规则集原样落盘，而 `headerOverrides` 里通常躺着目标环境的 `Authorization`，`queryOverrides` 里是 `token` / `api_key`——「把同一套配置交给同事」是文档里写了两年的场景，这条路径此前没有任何脱敏，分享一次就等于把联调 token 贴进群里。现在导出弹窗多了一个默认勾选的「分享模式」，下载前剔除三处位置的敏感条目：请求头覆盖、查询参数覆盖、响应头覆盖，比对方式为整名精确匹配（去首尾空白、转小写），名单是 16 个可能承载凭据的头名（`authorization` / `cookie` / `x-api-key` / `access-token` 等）与 11 个查询参数名（`token` / `api_key` / `code` / `password` 等）；刻意不做子串匹配，`x-token-refresh-interval` 这类计数头不该被误删。命中即**整条删除**而不是替换成占位值：塞 `***REMOVED***` 会被导入方原样发出、换回一个 401，看起来像规则坏了。请求体覆盖、Mock 正文与 `bodyRaw` 原样保留——那是规则要交付的内容，自动改写很可能让它不再是合法 JSON。取消勾选即原样导出（本机全量备份），两种模式都会正常下载；成功提示按移除数分成两句（「配置已导出」/「移除 $1 处敏感信息」），否则用户会把改写当成丢配置。判定收在 `utils/exportSanitize.ts`（纯函数、不就地修改入参、字段清空则删字段而不是留空对象、无命中时复用原规则对象），`tests/exportSanitize.test.ts` 另钉住勾选值确实贯通到下载内容。
  **Export defaults to "share mode", so credentials no longer travel with the file.** The exported JSON was the rule set verbatim, and `headerOverrides` typically held the target environment's `Authorization` while `queryOverrides` held `token` / `api_key` — handing a config to a colleague has been documented for two years, and that path never scrubbed anything, so one share pasted the session token into a group chat. The export dialog now carries a ticked-by-default share mode that strips sensitive entries from three places before the download: request header overrides, query-parameter overrides and response header overrides. Matching is whole-name (trimmed, lower-cased) against 16 header names that can carry credentials (`authorization`, `cookie`, `x-api-key`, `access-token`, …) and 11 query names (`token`, `api_key`, `code`, `password`, …); deliberately no substring matching, so a counting header like `x-token-refresh-interval` survives. A hit deletes the entry rather than replacing its value with a placeholder — `***REMOVED***` gets sent verbatim by the importing side and comes back as a 401, which reads as a broken rule. Request body overrides, mock bodies and `bodyRaw` are untouched, since that payload _is_ what the rule delivers and rewriting it is a good way to make it invalid JSON. Unticking exports verbatim (a full local backup) and both modes download normally; the success toast splits into two wordings by removed count, because otherwise the rewrite looks like lost configuration. The decision lives in `utils/exportSanitize.ts` (pure, never mutates its input, drops a field instead of leaving an empty object, reuses the original rule object when nothing was stripped), and `tests/exportSanitize.test.ts` additionally pins that the checkbox value reaches the downloaded file.
- **规则列表与 URL 匹配预演标出「浏览器不会应用这条规则」**：正则规则由网络层（`declarativeNetRequest`）承载时用的是 RE2 引擎，环视（`(?=…)`、`(?<=…)`）与反向引用都不被支持；目标 URL 的捕获引用也可能越界（`\2` 而正则只有一个组）。这两种规则在界面上是「已启用」、绿点正常，同步阶段却被静默跳过——而拦截器只接复杂规则，于是它同时不被 SW 通道接管，对流量零作用，用户唯一的线索是「怎么代理没生效」。现在 `utils/dnrSupport.ts` 把后台同步用的同一套判据（`isSimpleRule` + `isRegexSupported` + `isSubstitutionValid`）搬到界面侧，规则名后挂一枚红色「未生效」徽章（悬停给出原因与改法：换成通配符/前缀，或加上方法过滤、请求头覆盖等任一项能力让它改走代理通道），规则计数行补一句「其中 $1 条规则不会被应用」，URL 匹配预演的通道标签从「绿色 DNR」变成「红色 DNR + 说明」，保存规则时若刚存的这条正是被跳过的那条，成功提示直接换成可行动的警告。判定**只诊断、不改分流**——规则走哪条通道仍然只由 `isSimpleRule` 决定；它也是异步的（RE2 校验走 chrome API），所以结果是每次规则变化重算的 ref，并丢弃过期结果避免并发覆盖。
  **The rule list and the URL match tester now flag "Chrome will not apply this rule".** When a regex rule rides the network layer, RE2 is the engine, so lookaround (`(?=…)`, `(?<=…)`) and backreferences are unsupported; a capture reference in the target URL can also be out of range (`\2` against one group). Such a rule shows as enabled with a healthy green dot while the sync step silently skips it — and since the interceptor only takes complex rules, it is not picked up by the SW channel either, leaving it with zero effect and "why isn't anything proxied" as the only clue. `utils/dnrSupport.ts` moves the very predicates the background sync uses (`isSimpleRule`, `isRegexSupported`, `isSubstitutionValid`) to the UI side: a red 未生效 badge after the rule name (hover gives the reason and the fix — switch to wildcard/prefix matching, or add a SW-only capability so the rule takes the proxy channel), a "of which $1 will not be applied by Chrome" line beside the rule counter, a danger-coloured channel tag with an explanation in the URL match tester instead of a reassuring green "DNR", and an actionable warning in place of "rule saved" when the rule you just stored is one of them. The check **diagnoses only, it never changes routing** — the channel is still decided by `isSimpleRule` alone — and being asynchronous, its result is a ref recomputed whenever the rule set changes, with stale results discarded.
- **URL 匹配预演补上 DNR 通道的 CORS 边界**：预演里判定为「DNR（浏览器网络层）」的规则此前只报通道，读者据此以为请求已经由扩展代发。但 DNR 只在网络层改写 URL，响应不经过扩展，同源策略照常生效——目标环境没返回匹配的 `Access-Control-Allow-Origin` 时浏览器仍然拦截，这正是「规则命中了、控制台还是报 CORS」的原因，而解法（给规则加任一项高级能力，让它改由扩展代发）就在同一个弹窗里却没人联想到。现在通道标签下方固定一段说明：讲清这一通道仍是一次跨域请求，并指出加上请求头覆盖、方法过滤或 Mock 中任一项即切换到扩展代发，扩展上下文不受 CORS 限制。
  **The URL match tester states the CORS boundary of the DNR channel.** A rule classified as DNR (network layer) used to be reported as a channel and nothing more, which readers took to mean the extension was making the request. It is not: DNR rewrites the URL in the network layer and the response never passes through the extension, so same-origin policy still applies and a target without a matching `Access-Control-Allow-Origin` is still blocked — exactly the "the rule matched but the console still says CORS" case, whose fix (give the rule any advanced capability so the extension fetches instead) sits in the same dialog but was not connected to it. A short paragraph now sits permanently under the channel tag, and both wordings live in the locale files.

- **配置被写成「规则不是数组」时，徽章、代理状态与页面侧规则同步不再半途抛错**：工具栏徽章的数字是总开关在界面上唯一的落点，`storage.onChanged` 监听器与启动时的 `initBadge`、弹窗读的 `getProxyStatus` 三处都直接对存储里的 `config.rules` 调 `.filter()` / `.map()`。手改过一份配置（或一份被截断的旧数据）就能让那个键变成一个对象、一个字符串，三处全部当场抛 `TypeError`，而**只有监听器那一处没有接手人**：徽章从此**停在改动前那个数字**（用户看到的是「还在代理，N 条规则」，而真实数字早已作废）。另外两处各有接手人，代价是读数看不出来源——`initBadge` 自己 catch，只留一行 error 日志、徽章一个字符都不画；`getProxyStatus` 经 `respondAsync` 回成错误信封，弹窗沿用上一次读数而不报「读不到」。现在取规则数组只有一个出口 `utils/storage.ts` 的 `configRules()`，非数组一律当空——合法配置下三个消费点的数字与画面一个字都没变（`tests/badgeManager.test.ts` 同时钉住三态徽章与这条越界路径）。**一条已知边界没被这次收口覆盖**：监听器外面那层 `if (newConfig?.rules)` 在键整个不见（或为 `null` / `''`）时压根不重算，徽章同样停在旧数字——它要改的是「什么时候重算」，属于既有语义取舍，先如实记着。同一条判据在**两个内容脚本 world 各自落地**（桥接层的 `toInterceptorConfig`、拦截器的 `SYNC_RULES` 分支），因为它们引不到那个出口：MAIN world 自包含，桥接层一旦引它就把存储门面连带一个用不到的 `chrome.storage.onChanged` 监听拖进每个 frame。那两处原本写的是 `?? []` 与 `|| []`，只挡空值、不挡对象。桥接层那一处的抛出分两条路径：广播路径抛在 `sendResponse` 之前，送达账会把这一页记成未同步（弹窗那句「尚未收到最新配置」说得出）；页面主动拉取那条路径抛在 `.catch(logger.debug)` 里，咽成一行 debug，于是这一页的复杂规则静默按原生路径发出。拦截器那一处则是入站判据——同页脚本拿着 `CHANNEL` 字面量就能自己 postMessage 一条 `SYNC_RULES`（`event.source === window` 挡不住它），少这道判据，规则缓存停在上一份好配置而这一页看起来仍在被代理。存储的**写入**路径刻意两边都不用：那里 `rules` 不是数组就该失败得响亮，当成空数组写回去等于抹掉用户已有的规则。随这条一起补上的是两个此前零行为测试的后台模块：`tests/autoOff.test.ts` 钉住自动关闭倒计时的五条不变量（关闭或时长 0 就清掉、开启且有时长才建、**改别的规则不给它续命**、时长刚改过才按新值重建、到期那一刻关的是总开关），徽章那条「灰底 OFF / 蓝底数字 / 无规则清空」的三态也各有其主。自动关闭本身行为未改：这些是它一直没有的承诺，不是新加的能力。
  **The badge, the proxy-status read and the page-side rule sync no longer throw when the stored config's rules field isn't an array.** The number on the toolbar icon is the only place the global switch shows up outside the popup, and three readers — the `storage.onChanged` listener, the startup `initBadge`, and the popup's `getProxyStatus` — each called `.filter()` / `.map()` straight on `config.rules` as read from storage. A hand-edited (or truncated, older) value turns that key into an object or a string and all three throw `TypeError` on the spot, but **only the listener has nobody catching it**: the badge then **freezes on whatever number preceded the change**, telling the user "proxying, N rules" long after that number stopped being true. The other two do catch, at the cost of a reading with no visible origin — `initBadge` swallows it into one error log and draws no badge text at all, while `getProxyStatus` comes back as an error envelope through `respondAsync`, so the popup quietly keeps whatever it read last. There is now a single exit for the rule array, `configRules()` in `utils/storage.ts`, which treats anything non-array as empty — under a well-formed config the three readers show exactly the same numbers and the same icon as before (`tests/badgeManager.test.ts` pins the three badge states alongside this out-of-bounds path). **One boundary this does not reach:** the listener's outer `if (newConfig?.rules)` never recomputes when the key is simply gone (or `null` / `''`), so the badge freezes there for the same reason — closing that means changing _when_ the badge recomputes, an existing-semantics tradeoff, recorded rather than decided. The same check lands **separately in each content-script world** (`toInterceptorConfig` in the bridge, the `SYNC_RULES` branch in the interceptor), because neither can reach that exit: MAIN world is self-contained, and importing it into the bridge would drag the whole storage façade — plus a `chrome.storage.onChanged` listener that world never uses — into every frame. Those two sites previously wrote `?? []` and `|| []`, which tolerate a missing value but not an object. In the bridge the throw has two shapes: on the broadcast path it lands before `sendResponse`, so the delivery ledger marks the tab unsynced and the popup does say "this page hasn't picked up the latest config"; on the page's own pull it lands inside a `.catch(logger.debug)`, which reduces it to one debug line while every complex rule on that page quietly goes out natively. In the interceptor the check is an inbound one — a script in the same page can post its own `SYNC_RULES` with the `CHANNEL` literal (`event.source === window` does not stop it), and without the guard the rule cache then rests on the last well-formed config while the page still looks proxied. The storage **write** paths deliberately use neither: a non-array `rules` there should fail loudly, because treating it as empty and writing it back would erase the user's own rules. Alongside it come behaviour tests for two background modules that had none: `tests/autoOff.test.ts` holds five invariants of the auto-off countdown (cleared when the switch is off or the duration is 0, armed only when on with a duration set, **editing other rules never extends it**, rebuilt at the new value only when the duration itself changed, and expiry flipping the global switch), while "grey OFF / blue count / blank with no rules" is now pinned per state. The countdown's behaviour is unchanged — these are promises it never had tests for, not new capability.

- **复杂规则在 iframe 里从来没生效过**：两个内容脚本入口都只声明了 `matches: ['<all_urls>']`，没有 `allFrames`，Chrome 因此只把它们注入顶层框架。页面把请求发在 iframe 里时（嵌入式表单、报表、第三方 SDK 自建 iframe 都很常见），那个 frame 里既没有拦截器去改写 `fetch` / `XMLHttpRequest` / `WebSocket`，也没有桥接层把请求送进后台，于是请求原样按原生路径发出。网络层（DNR）通道不受影响——它在浏览器进程里改写 URL，与 frame 无关——所以症状恰好是「同一个地址在主页能代理、嵌进 iframe 就不行」，而界面上没有任何对应的迹象：弹窗那一行只数得到顶层的账，日志里也压根没有那一笔。现在两个入口**成对**声明 `allFrames: true`：只加一边就是半份注入（桥接在 iframe 里收发正常，但对端拦截器不存在），比整页不生效更难查，这一条由 `tests/channel-consistency.test.ts` 按源码契约钉住。代价是注入面扩大到页面的全部 frame，拦截器留下的痕迹随之增多——配置下发仍按 `toInterceptorConfig` 收窄，凭据字段依旧不进页面 world。多 frame 之下「这一页」的账也跟着改：四个计数是各 frame 自己从 1 数起的，后台的交叉校验基线因此按 `(tabId, frameId)` 各记一本，否则顶层已代发 3 笔就会把 iframe 那份诚实的 `proxied: 1` 判成谎话整包丢弃、弹窗那一行冻结在旧读数上；读端再把各 frame 的数求和（`updatedAt` 取最近一次被采信的时刻），界面说的仍是整页一个结论。取消代发请求的登记键同样补上 `frameId`，理由一样——`requestId` 只在 frame 内唯一，否则一个 frame 能掐断兄弟 frame 在跑的那笔。一处已知边界：`tabs.onUpdated` 只跟主框架的导航，iframe 单独换文档时它那本账不会复位，表现是那一行停在旧读数（陈旧，不是假数），刻意不为此加 `webNavigation` 权限。
  **Complex rules never applied inside an iframe at all.** Both content-script entries declared `matches: ['<all_urls>']` without `allFrames`, so Chrome injected them into the top frame only. When a page issued its requests from an iframe — routine for embedded forms, reports, and the frames a third-party SDK builds — that frame had neither the interceptor rewriting `fetch` / `XMLHttpRequest` / `WebSocket` nor the bridge that hands requests to the background, so they simply went out natively. The network layer (DNR) was never affected, because it rewrites URLs inside the browser process regardless of frame, which made the symptom exactly "this address proxies on the page but not inside the iframe" with nothing on screen to match it: the popup line only ever counted the top frame and the log held no trace of the request. Both entries now declare `allFrames: true` **as a pair** — one without the other is a half injection (the bridge talks normally inside the iframe while its counterpart interceptor does not exist there), which is harder to diagnose than a page that never works at all, and the pairing is held by source contract in `tests/channel-consistency.test.ts`. The cost is that injection now covers every frame of the page, so the interceptor's footprint grows with it; config delivered to the page is still narrowed by `toInterceptorConfig`, and credential fields still never enter a page world. Accounting for "this page" follows suit: the four counters are each frame's own count from 1, so the background's cross-check baseline is kept per `(tabId, frameId)` — otherwise three requests already proxied by the top frame would brand the iframe's honest `proxied: 1` a lie and drop the packet, freezing the popup line on a stale reading — and the frames are summed only on the read side (`updatedAt` takes the most recent accepted report), so the interface still states one conclusion for the whole page. The registration key for cancelling a proxied request gains the same `frameId` for the same reason: `requestId` is only unique inside a frame, and without it one frame could cut off a sibling frame's in-flight request. One known boundary: `tabs.onUpdated` follows main-frame navigation only, so an iframe that swaps documents on its own keeps its stale account, which shows up as that line resting on an older reading (stale, never fabricated); no `webNavigation` permission is added for this.

- **页面取消只丢掉迟到的响应，后台那笔代发照旧跑完**：被代理的 fetch / XHR 此前没有把页面的取消信号透传给后台，页面 `abort()` 之后拦截器只是把晚到的响应扔掉——上游连接继续占用，开着「携带 Cookie」时凭据继续外发，配了重试的规则还按间隔追加下一次尝试，配了延迟时甚至先睡满延迟再出发。现在页面的取消经一条新的 `CANCEL_REQUEST` 消息（拦截器 → 桥接层 → 后台）送到 SW，按登记键掐断正在跑的这笔：`AbortController` 触发、`xhr.abort()`、页面自己设的 `xhr.timeout` 到期，三条路径都覆盖；延迟期间被取消时上游请求根本不再发出（等待改为可被打断），日志记 `Cancelled by page` 与超时分开，且刻意**不**算一次可重试的失败——否则「取消」反而多打几下上游。四道边界：页面已取消时拦截器原样抛出 `signal.reason`（页面普遍按 `err.name === 'AbortError'` 分支），绝不回退原生 fetch，那等于把页面刚放弃的请求再发一遍；登记键带 `tabId` 与 `frameId`，因为 `requestId` 是每个 frame 各自从 1 开始数的计数器，否则一个标签页能掐断另一个标签页在跑的那笔、一个 iframe 也能掐断同页兄弟 frame 的那笔；`CANCEL_REQUEST` 与 `PROXY_REQUEST` 同档**不设** `isTrustedSender` 门禁（内容脚本的 `sender.url` 就是页面 URL），越权面由键本身挡住；桥接层转发时载荷收窄成一个 requestId，不顺带递出 URL 与请求头，回执在页面侧没有读者因此不等也不重试。已知边界：Mock 分支自己那段 `delayMs` 等待不参与取消（它不握上游连接，也没有重试要停）；WebSocket 由页面直连，扩展侧没有代发请求可取消；一笔被取消的请求仍在日志里占一行。`tests/cancelProxiedRequest.test.ts` 覆盖后台侧（经真路由的两侧键一致、跨标签页与跨 frame 都不误伤、非法载荷、取消不被重试），`tests/cancelRequestPropagation.test.ts` 按源码契约钉住页面侧三条取消路径与桥接层的收窄转发。
  **A cancelled page request only discarded the late response while the background fetch kept running.** Proxied fetch and XHR calls never carried the page's abort signal across, so after the page gave up the interceptor simply dropped the response that arrived too late: the upstream connection stayed open, credentials kept going out on rules with "send cookies" on, a rule with retry kept adding attempts on its own schedule, and a configured delay was slept through before the request departed at all. Cancellation now reaches the worker over a new `CANCEL_REQUEST` message (interceptor → bridge → background), which aborts the in-flight request by its registration key, covering all three ways a page gives up — an `AbortController` firing, `xhr.abort()`, and the page's own `xhr.timeout` expiring. A cancel that lands during a delay means the upstream request is never issued (the wait is now interruptible), the log records `Cancelled by page` separately from a timeout, and a cancel is deliberately **not** a retryable failure, because that would make cancelling hit the upstream more times. Four boundaries: once the page has aborted, the interceptor rethrows `signal.reason` untouched (pages branch on `err.name === 'AbortError'`) and must never fall back to native fetch, which would re-send exactly the request the page just abandoned; the key carries `tabId` and `frameId` because `requestId` is each frame's own counter starting at 1 — otherwise one tab could cancel another tab's running request, and one iframe could cut off a sibling frame in the same page; `CANCEL_REQUEST` sits in the same bracket as `PROXY_REQUEST` and is deliberately **not** gated by `isTrustedSender` (a content script's `sender.url` is the page URL), with the key itself limiting the damage; and the bridge narrows the forwarded payload to the id alone rather than passing the URL and headers along to a handler that only needs the id — nothing reads the acknowledgement on the page side, so it neither waits nor retries. Known boundaries: the `delayMs` wait inside the Mock branch is not cancel-aware (it holds no upstream connection and has no retries to stop); WebSocket connections are made by the page, so there is no proxied request to cancel; a cancelled request still occupies one row in the log. `tests/cancelProxiedRequest.test.ts` covers the background side (both halves of the key built from the same tab and frame through the real router, no collateral across tabs or frames, invalid payloads, cancel never retried), and `tests/cancelRequestPropagation.test.ts` holds the three page-side cancel paths and the bridge's narrowed forward by source contract.
- **后台代发的 30 秒截止只管到响应头，读 body 那一段没有任何超时**：`clearTimeout` 落在 `await fetch()` 之后，而 `content-type` 含 `text/` 或 `application/json` 的响应接下来还要 `await response.text()`，此后的读取阶段再无截止。`text/event-stream` 这类不结束的流因此把上游连接一直握到后台被回收，而请求日志是在 body 读满之后才落的，所以这条请求在日志里根本不存在；页面只能等它自己的兜底超时（延迟 + 单次 30 秒 ×（重试次数+1）+ 重试间隔 × 重试次数 + 5 秒余量），配了延迟或重试时是几分钟——文档、落地页与 FAQ 里那句「单个代理请求 30 秒上限」在这段时间里并不成立。更要紧的是「慢但最终成功」这一类：body 在页面兜底之后才落地时，后台交回的是 200，页面已经报错，日志一条 200、界面一次失败，两边各说各话。现在截止定时器改在 `finally` 里清除，30 秒覆盖「拿到响应头 + 读满 body」整段：读 body 拖过截止会像连接超时一样按失败收口（错误文案仍是 `Request timeout (30s)`，开重试的规则照常追加下一次尝试，两端看到的都是同一次超时）。刻意只补这一半——**body 体积上限**同样缺失，但加它会让用户当前「慢但拿得到」的大响应变成「被截断」或「被拒」，那是需要单独拍板的取舍。`tests/proxyDeadline.test.ts` 钉住两端：30 秒内读满的快响应原样返回、不受影响；40 秒才落地的 body 不再被采纳，且断言它是在截止处被掐断的（不是等那笔迟到的 body 之后才失败）。
  **The 30-second deadline on a background-proxied request was dropped as soon as the response headers arrived, leaving the body read unbounded.** `clearTimeout` ran right after `await fetch()`, but a response whose `content-type` contains `text/` or `application/json` still has `await response.text()` in front of it, and that read had no deadline at all. A stream that never ends (`text/event-stream`) therefore held its upstream connection until the worker was recycled, and since the log entry is written only after the body is read, the request left no trace in the log drawer either — the page just waited for its own backstop (configured delay + 30 s × attempts + retry interval × retries + 5 s of slack), which is minutes once delay or retry is configured, so the "30-second cap per proxied request" stated in the docs, landing pages and FAQ was not true during that window. Worse was the slow-but-successful case: a body that landed after the page gave up produced a 200 in the background and an error in the page, i.e. a log line and a screen that contradict each other. The timer is now cleared in `finally`, so the 30 seconds cover headers _and_ body: an over-run fails exactly like a connection timeout (same `Request timeout (30s)` text, and a rule with retry still makes its next attempt) and both ends agree on one timeout. Deliberately only this half — a **body size cap** is equally missing, but adding one would turn a response the user currently gets slowly into a truncated or refused one, which is a trade-off worth its own decision. `tests/proxyDeadline.test.ts` pins both ends: a body that arrives inside the deadline comes back untouched, and one landing at 40 s is never adopted — asserted to be cut at the deadline rather than failing only after the late body landed.
- **规则列表把「这条规则不走该通道」画成 0，读起来像一次都没命中**：命中列的两格此前只有网络层那一格会画「—」，后台通道那一格无条件输出 `stat.ext`。于是一条走网络层的简单规则显示成「N / 0」，而那个 0 的意思不是「一次也没走后台」，是「这条规则根本不在后台执行」——扩展通道的计数器只累加经后台代发的请求，简单规则在网络层就被重定向了，永远碰不到它。反向同理：复杂规则在网络层读到 0 时是真 0，读不到时又与「没有这类规则」共用一句提示。现在两格各自先问「该不该有读数」、再问「读到了没有」：通道逐条由 `isSimpleRule` 判定（刻意不看总开关，否则刚被禁用的网络层规则会在近 5 分钟滚动窗口里丢掉它真实的命中数），不适用的一格画「—」并配上各自点名通道的悬停提示，两格都是「—」时仍折叠成整列的「-」。`tests/dnrSample.test.ts` 按源码契约钉住这套判定与两句互斥话术。
  **The rule list was rendering "this rule doesn't use that channel" as a 0, which reads as "it never hit".** Of the two hit cells, only the network-layer one could draw an em dash; the background cell printed `stat.ext` unconditionally. A simple rule redirecting at the network layer therefore showed as "N / 0", where the 0 does not mean "not once went through the background" but "this rule never runs in the background" — the extension-channel counter only accumulates requests the worker fetches, and a simple rule is rewritten before that ever happens. The reverse held too: a genuine 0 in the network cell was indistinguishable from "no reading available", because both shared one tooltip. Each cell now asks "should there be a reading here?" before "did we get one?": the channel is decided per rule by `isSimpleRule` (deliberately not by the global switch, which would erase a just-disabled network rule's real hits inside the rolling five-minute window), a non-applicable cell draws an em dash with a hint that names its own channel, and rules with two dashes still collapse to the column's single "-". `tests/dnrSample.test.ts` holds the decision and the two mutually exclusive wordings by source contract.
- **四处把能力与统计口径说反的文案**：①WebSocket 徽标、两份落地页与 `llms.txt` 的「长连接上不生效」清单少了刚上线的「携带 Cookie」——那条开关靠后台代发时的 `credentials`，长连接的地址重写发生在网络层、握手也由浏览器直接发出，扩展无从干预，清单不写就等于宣称长连接也能带上你在目标环境的会话。②扩展通道的悬停提示只说「自上次配置变更累计」，而它同样是后台被回收即归零的内存计数，用户据此以为数字会一直涨，现在补上「或后台重启」。③弹窗的「本页 · 近 5 分钟」那一格在总开关关闭时说「无生效的网络层规则」，与同屏的「活跃规则 N」正面矛盾——开关一关动态规则被整体撤下，此刻用户的事实只有「代理未开启」，于是按开关二次分因；首次采样在途与配额退避也不再留空白注释，画了「—」却不给理由只能靠猜。④「接口请求是否被代理请看『本页』计数」没有说明那一格只覆盖网络层，读日志的人据此以为后台命中也显示在那里，现在两句都点名通道。
  **Four wordings that misstated what a capability or a counter covers.** (1) The WebSocket badge, both landing pages and `llms.txt` listed what does _not_ apply to a socket but omitted the "send cookies" switch that just shipped: it works by having the background fetch with `credentials`, whereas a socket's rewrite happens in the network layer or the browser performs the handshake itself, so leaving it out read as a claim that sockets carry the target session too. (2) The extension-channel tooltip said "since the last config change" only, while the count is in-memory and resets when the worker is recycled; it now says so, because readers otherwise assume the number only climbs. (3) With the global switch off, the popup's "This tab · 5 min" cell said "no network-layer rules", which contradicts the "N active rules" sitting on the same screen — turning the switch off uninstalls the dynamic rules, so the user's actual fact at that moment is "proxy is off"; the note now splits on the switch, and the first-sample-in-flight and quota-backoff cases no longer render a bare dash with no reason. (4) "For API requests see the This-tab count" never said that cell only covers the network layer, so readers looked there for background hits too; both languages now name the channels.

- **页面已经选好的规则被后台重匹配抢走，被阻断的请求因此真的发了出去**：桥接层只把复杂规则下发给页面，MAIN world 拦截器按这份窄列表选中规则、改写并代发，而 SW 收到 `PROXY_REQUEST` 后拿的是**完整**规则集重新匹配。只要另有一条更宽、优先级更高的简单规则覆盖同一个地址，SW 就选中它：窄规则的请求头覆盖与 Mock 静默失效，页面以为拿到了假数据其实打到了真上游；窄规则是 `blocked` 时更糟——SW 认为这条不该挡，请求原样发出，「阻断」这项能力在页面上可被一条无关规则绕过，而这正是它最要紧的失败模式。拦截器现在把自己选中的 `ruleId` 随请求发出，SW 侧由 `resolveSelectedRule` 复核后才采纳：规则存在、仍启用、并用同一条 `matchRule` 对这次请求的 url/method 仍然命中，任一不成立就回落到全量重匹配。这个 id 来自页面、属不可信输入，因此只当**候选校验**用——伪造它拿不到别的规则的能力，规则刚被删掉也只是退回修复前的行为。不带 `ruleId` 的调用方（弹窗的 URL 匹配预演、旧版本页面残留的在途请求）路径不变。`tests/proxyRuleSelection.test.ts` 覆盖六条行为与一条源码契约（拦截器的 fetch / XHR 共用出口必须带上 `ruleId`）。

- **同步 XHR 被悄悄异步化，页面读到一个空响应**：`xhr.open(method, url, false)` 的契约是「`send()` 返回时结果已在实例上」，而代理要经 `postMessage` 往返 ISOLATED world 与 SW，响应只能在调用栈返回**之后**到达。此前拦截器不区分同步与异步，同步调用的 `send()` 立即返回，页面接着读 `status` / `response` ——拿到 0 和空串，比抛错更糟，因为它读起来像「服务端返回了空响应」，排障方向当场被带偏。现在 `open()` 记住第三实参**显式为 `false`**（省略即异步，那是 XHR 的默认值），这类请求回退原生 `send()`，与 `FormData` / `Blob` 等非字符串 body 同一处置——代理不了就等价于没装本扩展，绝不用一个看起来能用的假结果冒充；阻断规则仍是唯一例外，回退等于把用户明确要求挡掉的请求真的发出去。回退提示一个页面只打一次，因为同步 XHR 常常写在轮询循环里。
  **Synchronous XHR was being quietly turned asynchronous, handing the page an empty response.** `xhr.open(method, url, false)` promises that the result is on the instance when `send()` returns, but a proxied request has to round-trip through the ISOLATED world and the service worker, so the response can only arrive after the call stack has unwound. The interceptor had not distinguished sync from async: `send()` returned immediately and the page read `status` 0 with an empty body — worse than an exception, because it looks exactly like "the server answered with nothing" and sends debugging off in the wrong direction. `open()` now records whether the third argument is **explicitly** `false` (omitting it means async, XHR's default), such calls fall back to the native `send()`, and the fallback sits alongside the one for non-string bodies: if it cannot be proxied it behaves like an uninstalled extension rather than passing off a plausible-looking fiction. Blocking rules remain the sole exception, since falling back there would send the request the user asked to stop. The fallback notice is logged once per page, because synchronous XHR tends to live inside a polling loop.
- **HAR 导出绕过了「分享模式」，凭据头原样落盘**：配置导出已经收在分享模式后面，HAR 却仍把日志原样转成 `.har`，而那里的 `requestHeaders` 记的是**浏览器真实发出去的头**——不是用户抄进规则里的覆盖头，而是页面自己带上的 `Cookie` 与 `Authorization`。于是同一份对话框里两个按钮共享一个「分享模式」勾选，只有一个按钮真的读它：取消勾选是"全量备份"，勾选了却还能从另一条路径拿到全量，脱敏形同存在但不生效。现在 HAR 与配置导出共用同一份判据（缺省脱敏，只有显式取消勾选才全量），实现在 `utils/exportSanitize.ts` 的 `sanitizeExportedLogs`：逐条剔除请求/响应头里的凭据类头名，正文与 URL 照旧保留——正文是复现问题必需的部分，删掉就只剩一份没用的骨架；URL 也不动，截断它等于打断「这条请求打到哪了」的追溯（与配置导出不同：那份还会剔掉 `queryOverrides` 里的 token 类参数）。导出弹窗另外补一句当前模式（开与关各一句），因为「HAR 是抓包，抓包当然原样」是这条路径上最自然的预期，不写出来用户不会知道自己拿到的是哪一种。`tests/exportSanitize.test.ts` 钉住两条路径共用勾选、缺省方向与提示文案。
  **HAR export skipped share mode and wrote credential headers straight to disk.** Config export had been put behind share mode, but HAR still converted logs verbatim, and `requestHeaders` there records what the **browser actually sent** — not the overrides the user typed into a rule, but the page's own `Cookie` and `Authorization`. Two buttons in the same dialog therefore shared one share-mode tick and only one of them read it: unticking meant "full backup", yet ticking it still left a path to the full set, which is a redaction that exists but does not hold. HAR now uses the same judgement as config export (redacted unless the box is explicitly unticked), implemented by `sanitizeExportedLogs` in `utils/exportSanitize.ts`: credential-like header names are dropped per entry, while bodies and URLs stay — the body is what a reproduction needs, and removing it leaves a skeleton nobody can use, while truncating the URL would break "where did this request actually go". (Config export is the one that also strips token-like names from `queryOverrides`.) The dialog also states which mode it is about to write (one wording per state), because "a HAR is a capture, captures are verbatim" is the most natural expectation on this path and an unstated mode is a mode misread. `tests/exportSanitize.test.ts` pins the shared tick, the default direction and both notices.
- **查询参数覆盖广播给了用不到它的页面**：桥接层下发配置前会剥掉「页面侧从不读取」的字段，因为 `postMessage` 的 targetOrigin 只挡跨窗口，同页面的任意脚本都能监听这些消息——把 `headerOverrides` 发给页面，等于把「把 token 从代码里挪进规则」省下的那笔凭据又还给了站点。`queryOverrides` 当时留在白名单里，理由是拦截器要用它，可实际只有 WebSocket 规则需要：长连接的地址重写在本 world 完成（`rewriteWsUrl` 会读这个字段），HTTP 侧的查询参数一律由 SW 追加。查询参数覆盖恰恰是放 token / `api_key` 的常见位置，于是每条 HTTP 规则都在把这个字段广播给它命中的站点，而页面上没有任何一处读它。现在非 WS 规则连 `queryOverrides` 一起剥，WS 规则保留并说明原因。`tests/interceptorConfigPrivacy.test.ts` 逐字段守住这条收窄面。
  **Query-parameter overrides were being broadcast to pages that could not use them.** The bridge strips fields the page never reads before handing down the configuration, because a `postMessage` targetOrigin keeps out other windows but not scripts on the same page — sending `headerOverrides` to the page hands back the credential that moving a token out of site code was meant to protect. `queryOverrides` had been left on the allowed list on the reasoning that the interceptor uses it, which is true only for WebSocket rules: a socket's URL rewrite happens in this world and reads that field, whereas on the HTTP path the background appends the parameters. Query overrides are exactly where a `token` or `api_key` tends to sit, so every HTTP rule was broadcasting that field to each site it touched while the page read none of it. Non-WebSocket rules now lose the field too, and the WebSocket case keeps it with the reason recorded. `tests/interceptorConfigPrivacy.test.ts` holds the narrowed surface field by field.
- **条件化 Mock 的 URL 正则绕过了 ReDoS 筛查**：嵌套量词的检测此前只长在 `getCompiledRegex` 那条路上，也就是规则的 `matchPattern` 会过筛，而条件化 Mock 的 `matchUrl` 是直接 `new RegExp(condition.matchUrl).test(url)`。两个字段的来源完全相同——表单与导入文件（HAR、cURL、JSON）都能写进去，导入侧也没有针对它的正则安全检查——所以一份"看起来正常"的配置文件带一条 `(a+)+$`，后台单个线程就在那次 `test()` 上转不完：不是某条请求失败，而是整个扩展停止响应，SW 卡死时连关闭总开关的点击都排不进去。现在 `matchesMockCondition` 编译前先跑同一道 `isRegexSafe`（从 `utils/urlMatcher.ts` 导出复用），不通过的判据是**该条件不匹配**而不是抛错——一条危险的 URL 条件不该连带废掉同规则其余条件与默认响应。良性量词（`/users/\d+`）照常工作。`tests/features.test.ts` 用三种嵌套量词形态钉住这条路径。
  **Conditional-mock URL patterns bypassed the ReDoS screen.** Nested-quantifier detection lived only inside `getCompiledRegex`, i.e. on the path for a rule's `matchPattern`, while `matchesMockCondition` went straight to `new RegExp(condition.matchUrl).test(url)`. The two fields share an origin — the form and every import channel (HAR, cURL, JSON) can write either, and neither the form nor the import side screened this one — so an otherwise ordinary config file carrying `(a+)+$` could leave the single-threaded service worker spinning inside one `test()` call: not a failed request but the whole extension going unresponsive, with even the click meant to turn the proxy off queued behind it. `matchesMockCondition` now runs the same `isRegexSafe` (exported from `utils/urlMatcher.ts` for reuse) before compiling, and a pattern that fails is treated as **not matching** rather than as an error, so one hazardous URL condition cannot take the rule's other conditions and its default response down with it. Benign quantifiers (`/users/\d+`) keep working. `tests/features.test.ts` pins the path across three nested-quantifier shapes.
- **刷写失败的日志要等下一条请求才落盘；网络层采样缓存的失效时机漏了一半**：两处时序。① `doFlushLogs` 取走快照时顺手摘掉了防抖定时器，写入失败后快照按时间顺序放回缓冲区等重试——可"下一次"要么等页面再发一个请求触发阈值，要么等 SW 被回收时那一下大概率来不及的 `onSuspend`；配额持续失败恰好是流量停止的时刻（日志写不进去，新请求还在往缓冲里堆），于是这一批日志两头落空。补盘挂在已有的 SW 保活心跳上（一分钟一次，空缓冲区在 `doFlushLogs` 开头直接返回，不产生写入），刻意不自建重试定时器：配额一直失败时后者会越滚越密，把本来就不宽裕的写入配额吃掉更多。② 采样缓存只在配置变更时丢弃，而动态规则集每次同步都是 `removeRuleIds` 全量重建，DNR ruleId 与代理规则的映射可能整体换一遍——旧窗口里的计数已经指向别的规则，缓存还按 60 秒的新鲜期继续供数，规则列表会把上一条规则的命中数画在这一条上。现在 `setDnrRuleIdMap` 之后同样调用 `invalidateDnrSample`，而退避窗口与滑窗计数刻意**不清**：配额是浏览器侧的真实事实，清掉只会让下一次注定失败。`tests/keepaliveFlush.test.ts` 与 `tests/dnrSampler.test.ts` 各守住一处。
  **Logs restored to the buffer after a failed flush waited for the next request, and the network-layer sample cache invalidated only half its triggers.** Two timing problems. (1) `doFlushLogs` clears the debounce timer as it takes the snapshot, and on failure the entries go back into the buffer awaiting a retry — but that retry needed either another page request to hit the threshold or the `onSuspend` that a recycling worker will not finish in time. Persistent quota failure is precisely the moment traffic has stopped writing usefully (new requests keep piling into the buffer while nothing lands), so the batch fell between both stools. The catch-up flush hangs off the service worker's existing keepalive alarm — once a minute, with an empty buffer returning early from `doFlushLogs` and touching no storage — deliberately not a new retry timer, which would compound on every failure and eat further into the quota it is waiting on. (2) The sample cache was dropped only on config changes, while each DNR sync rebuilds the rule set from scratch via `removeRuleIds`, so the mapping from DNR ruleId to proxy rule can rotate wholesale; counts from the previous window then point at different rules while the cache keeps serving for its 60-second freshness window, drawing one rule's hits beside another. `setDnrRuleIdMap` is now followed by `invalidateDnrSample`, while the backoff window and sliding-window tally are pointedly **kept**: the quota is a fact about the browser, and wiping the record only guarantees the next call fails too. `tests/keepaliveFlush.test.ts` and `tests/dnrSampler.test.ts` cover one each.

- **复用同一个 XHR 实例时请求永久挂起；后台内部错误文案不再广播给页面**：拦截器回填 `readyState` / `status` / `statusText` / `response` / `responseURL` / `responseText` 用的是 `Object.defineProperty`，却没带 `configurable`，而它默认是 `false`——页面对同一个 `XMLHttpRequest` 再次 `open()` + `send()`（轮询库与手写重试的常见写法）时，第二遍回填抛 `TypeError: Cannot redefine property`；抛出点在 `.then` 里，`.catch` 兜底又做同样的定义、再抛一次，于是 `error` / `loadend` 两个事件都派发不出来，那次请求在页面上永久 pending。15 处回填全部补上 `configurable: true`，并由 `tests/xhrReadonlyProps.test.ts` 按源码契约守住（拦截器自包含、跑在 MAIN world，行为测试覆盖不到）。另一处同性质：`normalizeProxyResponse` 的注释写着「失败信封的 error 文案不外泄给页面」，但 `...payload` 展开把 `error` 原样带进了广播给 MAIN world 的载荷，同源脚本因此能读到内网地址与驱动层报错；现在显式 `delete payload.error`，页面侧的错误信息仍由 `statusText` 承载（拦截器本来只读 `status` / `statusText` / `body`，两条路径的可见结果不变）。
  **Reusing an XHR instance no longer hangs the request, and the background's internal error text no longer reaches the page.** The interceptor backfills `readyState` / `status` / `statusText` / `response` / `responseURL` / `responseText` with `Object.defineProperty` but never passed `configurable`, whose default is `false` — so when a page called `open()` + `send()` again on the same `XMLHttpRequest` (what pollers and hand-rolled retries do), the second backfill threw `TypeError: Cannot redefine property` inside `.then`, and the `.catch` fallback threw again on the same definitions, leaving neither `error` nor `loadend` dispatched and the request pending forever in the page. All fifteen definitions now pass `configurable: true`, pinned by `tests/xhrReadonlyProps.test.ts` as a source contract (the interceptor is self-contained MAIN-world code, out of reach for behavioural tests). Same shape of bug elsewhere: `normalizeProxyResponse` documented "the failure envelope's `error` text is not leaked to the page" while `...payload` spread it straight into the message broadcast to MAIN world, where same-origin scripts could read internal hosts and driver-level errors; it is now explicitly deleted, and the page still learns the failure through `statusText` — the interceptor only reads `status` / `statusText` / `body`, so nothing visible changes.

- **204 / 205 / 304 响应与不合规的状态文本会让页面的请求永久挂起**：拦截器把后台回包交回页面时执行 `new Response(body, { status, statusText })`，而 Fetch 规范规定这三个状态码只能配 **null** 正文——空字符串同样非法，构造调用直接抛 `TypeError`。抛出点在 `resolve` 回调内部：超时已被 `clearTimeout` 摘掉，异常既不会变成 `reject` 也不会兑现 Promise，于是被代理的 `fetch` 从此永久 pending，比拿一个错误码糟得多（后端对 `If-None-Match` 回 304、对 DELETE 回 204 都是日常路径）。另一半约束是 `statusText` 属于 ByteString 且不得含换行：码点大于 255 的字符（后端写中文「查询成功」这类状态描述）与 `\r` / `\n` 都同样抛 `TypeError`——后者来自被手工拼出的状态行，实测 `new Response('', { statusText: 'OK\r\nX' })` 就是抛的。现在两处收敛都放在桥接层 `utils/proxyResponse.ts` 的 `normalizeProxyResponse`（`isNullBodyStatus` + `toLatin1StatusText`，只保留码点 ≤255 且非 CR/LF 的字符，制表符按规范留着；载荷类型随之改为 `body: string | null`），MAIN world 拦截器因自包含无法 import，在同一处镜像同一语义；后台侧的 Mock 状态码钳制本来就能落在这三个值上，因此这条路径真实可达。`tests/proxyResponseGuard.test.ts` 用「整形后的载荷真的能构造出 Response」钉住修复前抛错、修复后不抛，另有两条源码契约用例守镜像。
  **A 204/205/304 response, or a status text with codepoints above 255 or line breaks, used to hang the page's request forever.** The interceptor builds `new Response(body, { status, statusText })`, and the Fetch specification allows only a **null** body for those three statuses — an empty string throws `TypeError` too. The throw happens inside the `resolve` callback: the timeout had already been cleared, so the exception neither rejects nor resolves, leaving the proxied `fetch` pending forever, which is worse than an error code (304 for `If-None-Match` and 204 for DELETE are everyday paths). The other half is `statusText`, a ByteString that must not carry line breaks either: any codepoint above 255 — a Chinese status phrase from the backend — throws the same way, and so does the `\r\n` of a hand-built status line. Both constraints are now normalized in the bridge layer (`isNullBodyStatus` plus `toLatin1StatusText` in `utils/proxyResponse.ts`, which keeps only codepoints at or below 255 that are neither CR nor LF — tab stays, as the grammar allows — with the payload type following to `body: string | null`), mirrored in the self-contained MAIN-world interceptor, and reachable from the background too since a mocked status can land on exactly those values. `tests/proxyResponseGuard.test.ts` asserts the shaped payload really constructs a `Response`, plus two source-contract cases for the mirror.
- **响应头里的非 Latin-1 字符同样会让请求永久挂起**：上一条只管到 `statusText`，可 `new Response(body, { headers })` 的头名与头值同样是 ByteString——码点大于 255（规则里手写的中文响应头，表单与校验只看头名字符集和 CRLF，不管值）或含 CR/LF 都会让 `new Headers()` 抛 `TypeError`，抛出点照旧落在 `resolve` 回调里，页面那次 `fetch` 从此 pending。现在桥接层逐对剔除非法头名/头值、保留其余合法头（非字符串值仍整体回落为空对象，与原行为一致），MAIN world 镜像同一判据；`new Response()` 整段另外包进 `try/catch → reject`，因为形状约束是三处而不是两处，最后一道兜底不该把异常吞成永久挂起。`tests/proxyResponseGuard.test.ts` 补两条（码点 >255 的名/值被剔除且不误伤合法头、整形后的 headers 真能构造），`tests/interceptorResponseGuard.test.ts` 用源码契约守住镜像与 try/catch 两处。
  **Non-Latin-1 response headers hung the request the same way.** The previous entry covered `statusText`, but `new Response(body, { headers })` takes a ByteString for header names and values too, so a codepoint above 255 (a Chinese response header written into the rule — validation only looks at the name's charset and CRLF, never the value) or an embedded CR/LF makes `new Headers()` throw `TypeError` inside the same `resolve` callback, leaving the page's `fetch` pending forever. The bridge layer now drops illegal name/value pairs while keeping the rest (a non-string value still collapses the whole map to `{}`, exactly as before), the MAIN-world interceptor mirrors the same judgement, and the `new Response()` construction is additionally wrapped in `try/catch → reject`: the shape has three constraints, not two, and the last line of defence must not swallow an exception into a permanent hang. Two cases in `tests/proxyResponseGuard.test.ts` (codepoints above 255 pruned without touching valid headers; the shaped headers really construct) plus `tests/interceptorResponseGuard.test.ts` hold the mirror and the wrapper.
- **hash 直达与首次点击不再打开空白弹窗**：Options 的 7 个弹窗是 `defineAsyncComponent` 异步分片。两条路径会让分片**带着 `visible === true` 挂载**：`#add-rule`、`#add-rule-from-tab=`、`#profiles` 在父组件 `onMounted` 里同步置位，以及首次点击时分片尚未取回。此时只监听变化的 `watch(() => props.visible)`（无 `immediate`）永不触发。后果是三条静默故障：「编辑规则」打开一张空白表单，被编辑的规则连同其配置一起丢掉；从日志/Popup 带 hash 进来是同一个道理；环境配置弹窗靠 `el-dialog` 的 `@open` 拉列表，而该事件只在 `modelValue` 的 watcher 里发出，挂载即可见的那条分支根本不调它，列表永远空白；设置弹窗的自动关闭倒计时读不到配置，静默显示成「从不」。现在三处 watcher 统一带 `immediate`，`ProfilesDialog` 不再依赖 `open` 事件。`tests/full-verification.test.ts` 加三条源码契约：承担初始化/拉数据的 `props.visible` watcher 必须带 `immediate`、弹窗不得只靠 `open` 事件拉数据、hash 路由覆盖的入口其弹窗必须在守卫清单内（新增 hash 入口漏登记即红）。
  **Hash deep-links and first clicks no longer open empty dialogs.** The seven Options dialogs are `defineAsyncComponent` chunks, and two paths make a chunk mount with `visible` already true: the `#add-rule`, `#add-rule-from-tab=` and `#profiles` hash routes, which set it during the parent's `onMounted`, and a first click that lands before the chunk has been fetched. A `watch(() => props.visible)` without `immediate` never fires in either case. Three silent failures followed: "edit rule" opened a blank form and dropped the rule being edited; the same applied to hash arrivals from the log and the popup; the profiles dialog fetched its list from `el-dialog`'s `@open`, which is only emitted from the `modelValue` watcher and never for a dialog that is visible at mount, leaving the list permanently empty; and the settings dialog's auto-off countdown read nothing, quietly rendering "never". All three watchers now carry `immediate` and the profiles dialog no longer relies on `open`. Three source-contract cases cover it: a `props.visible` watcher that performs initialization must be `immediate`, a dialog must not fetch solely on the `open` event, and every hash-reachable dialog must be on the guard list.
- **一条小数优先级会让整批网络层规则同时失效**：DNR 的 `priority` 只接受整数，`toDnrPriority` 此前只做上下限钳制，于是优先级 2.5（在数字框里手敲，或来自导入文件）算出非整数，`updateDynamicRules` **整批**被拒——所有简单规则一起停摆，而不是丢一条规则。现在 `toDnrPriority` 取整（`Math.round`），导入侧 `normalizeImportedRules` 一并把小数优先级收敛为整数，表单的数字输入框锁上 `:precision="0"`、`:step="1"` 与 `step-strictly`，不再产出非法值。守卫分三层：`tests/dnrRules.test.ts` 断言混入小数时整批 priority 仍全为整数，`tests/round2-regression.test.ts` 盯住导入取整，`tests/full-verification.test.ts` 钉住输入框三项约束（缺任一项都能敲出 2.5）。
  **One fractional priority disabled every network-layer rule at once.** DNR accepts integer `priority` only, and `toDnrPriority` merely clamped range, so a priority of 2.5 — typed into the number input or coming from an imported file — produced a non-integer and `updateDynamicRules` rejected the **whole batch**: all simple rules stopped working at once rather than one rule being dropped. `toDnrPriority` now rounds, `normalizeImportedRules` folds fractional priorities into integers, and the form's number input pins `:precision="0"`, `:step="1"` and `step-strictly` so an invalid value cannot be produced in the first place. Three guards cover the layers: a batch-wide integer assertion in `tests/dnrRules.test.ts`, import rounding in `tests/round2-regression.test.ts`, and the input constraints in `tests/full-verification.test.ts`.
- **一条负得离谱的优先级同样会让整批网络层规则同时失效**：上一个坑的另一端。`toDnrPriority` 只钳下限，业务优先级为 -1000000000 时算出 `1000 - (-1e9) = 1000001000`，越过 Chrome 给动态规则的 priority 上限 1000000，`updateDynamicRules` 照旧整批被拒。表单的 1..999 永远到不了这个值，能到的是导入文件与手改的 `storage.local` 数据。现在反转结果两端钳制在 `[1, DNR_MAX_PRIORITY]`，正常区间的相对顺序一个字节都没动（`tests/dnrRules.test.ts` 同时钉住 `-500 → 1500` 不被钳平）。
  **A deeply negative priority disabled the whole batch too.** The other end of the previous bug: `toDnrPriority` clamped only the lower bound, so a business priority of -1000000000 computed `1000 - (-1e9) = 1000001000`, past Chrome's 1000000 ceiling for dynamic rule priorities, and `updateDynamicRules` rejected the entire batch again. The form's 1..999 can never reach that value — imported files and hand-edited `storage.local` data can. The inverted result is now clamped at both ends into `[1, DNR_MAX_PRIORITY]` without touching the relative order anywhere in the normal band (`tests/dnrRules.test.ts` also pins that -500 still maps to 1500).
- **日志的非正文字段不再绕过配额收口**：32K 的正文上限管不到 URL、方法、规则名与请求/响应头。页面一句 `fetch('https://a.com/?' + 'x'.repeat(5e6))`、一条超长 Cookie 头，就能把几 MB 字符写进 `storage.local`（本扩展未申请 `unlimitedStorage`），后果与正文超限一样：日志写不进去，连配置保存也一起失败。总量预算当时只累加正文，等于对这条路径完全放行。现在写入侧统一由 `capLogEntry` 收口——正文 32K 字符、其余文本字段 8K 字符、头表 64 条，预算（`MAX_LOG_BODY_TOTAL` → `MAX_LOG_TOTAL_SIZE`）改按整条日志的字符量累加。正常接口的 URL 与头表远在这几条线之内，日志抽屉里看不到任何差别。`tests/logQuota.test.ts` 覆盖四类收口，以及「裁过的可选字段不得新增 `undefined` 键」（HAR 导出靠 `!== undefined` 判断有没有响应体）。
  **Log fields outside the body no longer bypass the quota guard.** The 32K body cap never covered URLs, methods, rule names or header maps, so one `fetch('https://a.com/?' + 'x'.repeat(5e6))` from a page, or an oversized Cookie header, could push megabytes into `storage.local` (this extension does not ask for `unlimitedStorage`) with the same outcome as an oversized body: logs stop writing and saving config fails outright. The total budget only summed bodies, so it never saw that traffic either. Writes now pass one `capLogEntry` — 32K for bodies, 8K for every other text field, 64 entries per header map — and the budget (`MAX_LOG_BODY_TOTAL` → `MAX_LOG_TOTAL_SIZE`) counts the whole entry. Ordinary URLs and header sets sit far inside those lines, so the log drawer looks the same as before. `tests/logQuota.test.ts` covers all four caps plus the rule that a trimmed optional field must not gain an `undefined` key (the HAR export decides "was there a response body?" by `!== undefined`).
- **删除后 5 秒撤销窗口内的任何一次刷新都会捞出重复行**：删除是乐观更新——UI 立即移除，5 秒后才真正发 `DELETE_RULE`，为的是给「撤销」留退路。但这期间规则仍在 `storage.local` 里，于是任何一次 `fetchConfig`（其他标签页改了规则、导入配置、加载环境快照）都会把那行捞回来；用户再点撤销便 `splice` 出第二份，列表出现重复行，而按 id 的后续操作只会命中第一条。撤销窗口内删除消息的回包同样会漏。现在窗口期内的 id 登记在 `pendingDeleteIds` 集合里，由 `fetchConfig` 过滤掉，两条出口（用户撤销、删除已提交）都注销登记，否则删除成功后该行会被永久屏蔽。`tests/pendingDeleteUndo.test.ts` 覆盖登记/注销两侧与多条并发删除互不影响。
  **A refresh inside the five-second undo window resurrected the row as a duplicate.** Deletion is optimistic—the UI removes the rule immediately and sends `DELETE_RULE` five seconds later to leave room for undo—so during that window the rule still exists in `storage.local`, and any `fetchConfig` (another tab's change, an import, loading a profile) pulled it back. Clicking undo then spliced in a second copy, leaving a duplicate row whose later per-id operations only hit the first one; replies arriving during the window were dropped as well. Ids now register in `pendingDeleteIds` for the duration and are filtered out by `fetchConfig`, and both exits from the window (undo taken, delete committed) unregister, which is what keeps a successfully deleted row from being hidden permanently. `tests/pendingDeleteUndo.test.ts` covers registering, unregistering, and concurrent deletions not interfering.
- **非法请求头改在保存时拦下，而不是等到请求失败**：头名/CRLF 的判据此前只住在后台 `proxyHandler.ts` 里，规则表单却可以保存任意头名与含换行的取值——运行时 `validateRuleHeaders` 会整条拒绝（页面拿到 status 0，规则看起来「已启用却毫无作用」），而日志只能告诉用户这条被拒了。判据现在下沉为 `utils/headerValidation.ts` 供两侧共用，并新增两个出口：`findInvalidHeaderNames` 让表单在拼出待保存对象之前就报错、逐项列出问题头名（**只报头名不回值**，那里存的很可能就是凭据），`sanitizeImportedHeaderMap` 让导入路径逐条清洗而不是整条拒绝（导入文件不会回到表单让用户修正，静默丢掉脏头胜过让规则一落库就坏）。HAR 导入此前既不经表单也不经 `normalizeImportedRules`，等于留着一条无校验通道，现已接上同一套清洗。响应头覆盖同样在保存侧校验。
  **Invalid request headers are now rejected at save time, not at request time.** The header-name and CRLF checks lived only in `entrypoints/background/proxyHandler.ts`, so the rule form happily stored any header name and any value containing a line break; at runtime `validateRuleHeaders` rejected the whole rule (the page gets status 0 and an enabled-looking rule does nothing), and the log could only say it was refused. The predicates now live in `utils/headerValidation.ts` for both sides, with two new entry points: `findInvalidHeaderNames` lets the form fail before it builds the object, listing the offending **names only** — a value there is likely a credential — and `sanitizeImportedHeaderMap` makes the import path drop entries instead of rejecting the rule (an imported file never returns to the form for fixing, so dropping one dirty header beats storing a rule that breaks on first use). HAR import matched neither gate and was an unvalidated channel; it now runs through the same sanitizer. Response header overrides are validated on save too.
- **只配条件、或只配状态码的 Mock 会被静默丢弃**：写 `mockResponse` 的门是 `enableMockResponse && form.mockBody`，于是「按条件分别返回不同响应、默认响应体留空」和「只想让这条规则固定返回 500」这两种合法用法，点完保存提示成功，规则里却根本没有 Mock 字段。现在门同时看响应体、状态码与条件列表，任一有真实内容就写入；三者皆空时不假装保存，而是给一条「本次不会启用 Mock」的警告。`tests/round2-regression.test.ts` 钉住门的新条件与旧单条件门不得复现。
  **Conditional mocks, and mocks that only set a status code, were silently discarded.** The gate writing `mockResponse` was `enableMockResponse && form.mockBody`, so two legitimate uses — per-condition responses with an empty default body, and simply forcing a rule to answer 500 — saved "successfully" without the field ever being stored. The gate now considers body, status and conditions together and stores a mock if any carries real content; when all three are empty the user is told the mock was not enabled instead of being shown a success toast.
- **导入失败不再清空输入；替换模式补上限；合并进锁**：弹窗此前把数据 emit 给父组件后**立刻**清空文本域、清文件并关窗，而父组件的异步失败要晚一步到达——用户粘贴的 JSON 已经没了，只能重新粘贴。回传的 `error` 还是英文句子（`Merge would exceed max rules limit (200)`），直接透传进中文界面就是一句机器话。现在导入由弹窗自己发起并等待结果，失败时输入原样保留、弹窗不关，按稳定错误码（`INVALID_CONFIG` / `MAX_RULES_EXCEEDED` / 其余通用）分派本地化文案。存储侧一并收口三件事：替换模式此前完全不校验 `MAX_RULES`，一份超限的脏配置会整包落库；合并的「读 → 去重 → 拼 → 写」在存储锁外，会与并发的新增互相覆盖、静默丢掉另一边刚写入的规则；两种模式现在统一走 `importProxyConfig`，在锁内基于最新快照去重与校验，并回报新增/跳过数。去重逻辑随之从消息路由层搬到 `utils/ruleConflicts.ts`（只有持锁时才知道的现有规则集才该被依据）。HAR 导入同理：成功提示改由执行写入的父组件发出，达上限时不再与失败提示同时弹出、把输入提前清掉。另外，弹窗是异步分片、关掉后并不销毁，所以关闭动画结束（`@closed`，而不是新增 `props.visible` 的 watcher——该弹窗的源码契约就是「没有 visible watcher」）时清空已读内容与上传列表——否则重开弹窗一点「导入」就把同一批流量再导一遍，而 HAR 通道没有去重。
  **A failed import no longer wipes the input; replace gained the rule cap; merge moved inside the lock.** The dialog used to emit the payload to the parent and then immediately clear its textarea, its file list and close itself, while the parent's asynchronous failure arrived later — by which point the pasted JSON was gone. The `error` it received was an English sentence passed straight through into a Chinese UI. The dialog now runs and awaits the import itself, keeps the input and stays open on failure, and localizes by stable error code. On the storage side three things were closed together: replace mode never checked `MAX_RULES`, so an oversized file landed wholesale; the merge's read → dedupe → concat → write happened outside the storage lock and silently raced with concurrent additions; both modes now go through `importProxyConfig`, which dedupes and validates against the snapshot held under the lock and reports added/skipped counts. Dedup moved from the message router to `utils/ruleConflicts.ts`, since only the locked view of existing rules is authoritative. HAR import follows the same rule: the success toast comes from the component that performs the write, so a cap failure no longer shows both toasts and clears the input early. The dialog is also an async chunk that survives being closed, so the loaded text and the upload list are cleared when the closing animation ends (`@closed`, not a new `props.visible` watcher — this dialog's source contract is that it has none); otherwise reopening it and pressing Import would run the same traffic through a second time, and the HAR channel has no deduplication.
- **日志正文有了上限，写入失败也不再丢日志**：请求日志会存下请求体与响应体，而上限此前完全没设——一条超大 JSON 响应（代理请求体本来允许 10MB）就能把 `chrome.storage.local` 的配额（本扩展未申请 `unlimitedStorage`，约 10MB）撑满，后果不止是日志写不进，**连配置保存会一起失败**。现在单条正文超过 32K 字符即截断并标注原始长度（没有标记，用户会把截断的 JSON 当成完整载荷排查半天），收口放在存储层的 `capLogEntry`（当时只管正文）而不是各写入点——`proxyHandler` 有五条分支写日志，漏掉任何一处就是留一条无上限路径；未超限的条目原样返回（含 `undefined` 字段，HAR 导出靠 `responseBody !== undefined` 过滤，不能被写成空串）。单条有上限仍不总量安全：500 条 × 两条正文 × 32K 远超配额，故另设 4MB 总预算，超预算从最旧端丢弃，且预算再小也至少保留最新一条，否则「单条就超预算」会把整份日志清成空数组。刷写失败同样收口：快照已从缓冲区取走，此前一抛错就是静默丢日志，现在按时间顺序放回缓冲区等下次重试，而条数上限收口切掉的是最旧的一端，不再把刚发生的请求丢掉。顺带修掉一处既有倒序：一批日志此前被整批 `unshift` 到数组头部，而这份数组的约定是「头部是最新」，于是同批（最多 10 条）在日志抽屉里倒着排，缓冲区超过 500 条时环形缓冲切掉的还正是最新的那几条；现在入表按倒序插入，`tests/logQuota.test.ts` 既钉「补写的旧条目排在后面」，也钉「持续失败时留下的是连续的最新窗口」。`saveProxyConfig` 写入失败时也让缓存失效，避免内存里留下一份存储里并不存在的配置。
  **Log bodies are capped, and a failed write no longer loses entries.** The request log stores request and response bodies with no size limit, so one oversized JSON response (the proxied body limit is 10 MB) could fill the `chrome.storage.local` quota — the extension does not request `unlimitedStorage` — and the damage was not limited to logging: **saving the config failed too**. Bodies over 32 K characters are now truncated with the original length annotated (without it, readers debug a truncated payload believing it is complete), and the cap sits in the storage layer rather than at each call site because `proxyHandler` has five branches that write logs — miss one and an uncapped path remains. Untouched entries are returned as-is, `undefined` fields included, since HAR export filters on `responseBody !== undefined`. Per-entry caps are still not a total budget (500 × 2 × 32 K blows the quota), so a 4 MB budget trims from the oldest end while always keeping the newest entry — otherwise a single oversized entry would clear the whole log to an empty array. Flush failures were closed the same way: the snapshot had already left the buffer, so a throw silently lost logs, and it now goes back in chronological order, with the entry cap trimming the **oldest** end rather than the requests that just happened. One pre-existing inversion went with it: a flush prepended its whole batch at the head of an array whose documented convention is "head = newest", so a batch of up to 10 entries listed itself backwards in the log drawer, and once the buffer passed 500 the ring buffer dropped precisely the newest requests; the batch is now inserted reversed, and `tests/logQuota.test.ts` pins both "a retried entry lands behind the newer one" and "a persistently failing buffer keeps one contiguous newest window". `saveProxyConfig` also invalidates its cache on failure so memory does not hold a config that never reached storage.
- **搜索高亮不再把 `&` 显示成实体，也不再走 `v-html`**：旧实现先把文本转成 HTML 实体、再用正则往字符串里塞 `<mark>`，于是搜索 `amp` 会打断自己刚写的 `&amp;`、搜索 `;` 会让整格显示成乱码；更糟的是关键字为空时直接跳过转义——`<`、`>`、`"` 原样进 `v-html`，等于把用户输入当 HTML 解析（规则名和 URL 都来自导入文件与抓包，属于不可信输入），当时是靠一行 `eslint-disable vue/no-v-html` 压住的。现在 `utils/highlight.ts` 只做文本分段（关键字为空的分支同样存在，不再特殊处理原始文本），`HighlightText.vue` 按文本节点渲染，转义交回框架，`v-html` 与那行豁免一并删除。切片拼回原文、搜 `&`/`amp`/`;` 不打断内容、元字符按字面量匹配，由 `tests/highlight.test.ts` 逐条守住。
  **Search highlighting stopped mangling `&`, and stopped using `v-html`.** The old helper HTML-escaped the text and then regex-injected `<mark>` into the result, so searching `amp` broke the very `&amp;` it had just written and searching `;` turned a cell into mojibake; worse, an empty keyword skipped escaping entirely, sending raw `<`, `>` and `"` through `v-html` — parsing user input as HTML, on fields fed by imported files and captures — which was only kept quiet by a line disabling `vue/no-v-html`. `utils/highlight.ts` now only splits text into segments (with the empty-keyword case as a normal branch rather than a special raw path) and `HighlightText.vue` renders text nodes, letting the framework escape; `v-html` and the exemption are gone. `tests/highlight.test.ts` checks the segments reassemble to the original, that `&`/`amp`/`;` searches do not corrupt content, and that regex metacharacters match literally.
- **筛选不再清掉勾选，批量操作也不再作用在看不见的规则上**：搜索或按状态筛选时，`el-table` 拿到的是 `computed` 每次新生成的数组实例，没有 `reserve-selection` 的选择列会直接清空勾选——用户勾了五条、筛一下想找第六五条，回来只剩一条。开 `reserve-selection` 后跨筛选保留了，代价是勾选存活在表格内部：规则被批量删除、导入替换、切换环境之后，旧对象仍留在其中，父组件把自己的数组置空也清不掉，批量删除/迁移会静默命中当前筛选下根本看不见的规则；而「筛选无结果」分支的 `v-else` 会卸载整个表格，卸载时表格内部的保留勾选又静默丢失，父组件还拿着上一份。现在勾选源只存表格上报的原始列表，计数与批量操作一律经 `utils/ruleSelection.ts` 按 id 换算回**列表里的当前对象**（编辑过的规则不再是旧引用）并剔除已消失项；四个整体替换入口调用表格暴露的 `clearSelection()`；补发空勾选的触发点则是表格从「有行」翻回「无行」的那一刻——`RuleTable` 本身在页面内常驻，靠卸载钩子永远等不到。
  **Filtering no longer drops the selection, and batch actions no longer reach invisible rules.** Searching or filtering by status hands `el-table` a fresh array from a `computed` on every keystroke, and a selection column without `reserve-selection` clears itself — so after ticking five rules, one filter round leaves one. Turning `reserve-selection` on keeps the selection across filters, but it then lives inside the table: batch deletes, imports and profile loads leave stale objects that the parent cannot clear by emptying its own array, so a batch operation silently targets rules that are not even visible under the current filter; and the no-match branch unmounts the whole table via `v-else`, losing the reserved selection silently while the parent still holds the previous list. The raw table report is now the only selection source, while counts and batch actions go through `utils/ruleSelection.ts`, which resolves ids back to the **current objects in the list** (an edited rule is no longer a stale reference) and drops vanished ones; the four wholesale-replacement entry points call the table's exposed `clearSelection()`; and the empty selection is re-emitted the moment the table flips from rendering rows to rendering none — `RuleTable` itself stays mounted for the life of the page, so an unmount hook would never fire.
- **DNR 配置监听挪到同步阶段注册，不再漏掉唤醒它的那次变更**：`initDnrManager` 先 `await getProxyConfig()` 再注册 `storage.onChanged` 监听。若服务工作线程正是被这条配置变更唤醒的，事件在监听器挂上之前就已经过去——这批动态规则不会重新同步，表现是「改了规则没生效，直到我改下一次」。现在监听器在同步阶段注册，首次全量同步挪到之后异步执行（`initialSync`），两条路径不再抢先后顺序。
  **The DNR config listener registers synchronously, so it cannot miss the event that woke the worker.** `initDnrManager` awaited `getProxyConfig()` before registering `storage.onChanged`; when the service worker was woken _by_ that config change, the event had already fired before a listener existed, so the dynamic rules were never resynced — "I edited a rule and nothing happened until I edited it again". The listener now registers during synchronous startup, with the initial full sync moved to an asynchronous follow-up, so ordering can no longer be lost.
- **主题首帧不再闪默认配色**：`initThemeSync` 只靠 `chrome.storage.local.get`（异步 IPC）取偏好，于是首帧一律按默认调色板绘制，选了深色或其他主题色之后，每次打开配置页/弹窗都会先白一下再切换。现在与本地化偏好同一套做法：值同步镜像到 `localStorage`，启动时同步读出并立即应用，`chrome.storage.local` 仍是事实来源——异步读取若发现不一致会回写镜像并纠正渲染，`storage.onChanged` 同时更新两侧，多标签页之间照旧实时同步。一次 IPC 抖动不再抹平偏好：读取失败时镜像与当前渲染原样保留（镜像里上次成功读到的值仍比默认值更接近事实），写入失败时也不提前刷新镜像。镜像只存主题名与模式，不含任何用户数据。
  **The first frame no longer flashes the default palette.** `initThemeSync` read the preference only through the asynchronous `chrome.storage.local.get`, so every page painted the defaults first and switched after a round trip — visible as a white flash on each open for dark and custom themes. The preference is now mirrored synchronously to `localStorage` and applied at startup, exactly like the locale preference, with `chrome.storage.local` still authoritative: the async read reconciles and rewrites the mirror when they disagree, and `storage.onChanged` updates both. A single flaky IPC call no longer flattens the preference: if the read fails the mirror and the rendered palette are left untouched (the last value the mirror successfully captured is still closer to the truth than the default), and a failed write does not refresh the mirror ahead of the source. `tests/themeMirror.test.ts` pins both failure paths. The mirror holds only the theme name and mode.
- **cURL 导入的规则名带上方法**：粘贴 `curl -X DELETE https://api.example.com/x` 生成的草稿名是 `cURL: api.example.com`，与同一主域 GET 生成的完全同名——而规则本身不按方法过滤（导入只取 URL 与请求头），用户看不出这条草稿对应的是写操作，两条同名的规则在搜索与去重里还会互相顶掉。名字现在带上方法（`cURL: DELETE api.example.com`）。
  **A cURL import now names the rule after its method.** Pasting `curl -X DELETE …` used to produce `cURL: api.example.com`, identical to the rule made from a GET on the same host — and since the imported rule does not filter by method (only URL and headers are carried over), nothing hinted that this draft came from a write, while two same-named rules collide in search and in merge deduplication. The name now includes the method.

- **导航链接悬停与当前区块不再叠出两条下划线**：全站 `a:hover { text-decoration: underline }` 与页头那条自绘的 `.site-nav > a::after` 下划条同时生效，两条线在同一行底部并排出现，读者读作「这条菜单坏了」而不是「这条可点」；`.nav-actions` 里的三个出口同样中招。修法是在这两处显式 `text-decoration: none`，把下划线这一层表达完全交给自绘条，全局规则在正文链接上照旧。顺带把下划条从 `bottom: -5px` 挪到 `-6px` 并拆出独立过渡（`transform` 管长度、`opacity` 管强度）：悬停时是 45% 透明度的「可点」提示，滚动到的当前区块才是实心，两者不再是同一个视觉权重。`<a>` 上还补了 `:focus-visible { outline-offset }`，键盘焦点不再被那条下划条盖住。
  **Header links no longer draw two underlines at once.** The site-wide `a:hover { text-decoration: underline }` fired together with the header's own `.site-nav > a::after` bar, so hovering or landing on the current section stacked two lines at the bottom of the same row — which reads as a broken menu item, not an affordance. The three `.nav-actions` links had the same collision. Both now set `text-decoration: none` explicitly, leaving the underline expression to the drawn bar while the global rule keeps working everywhere in body copy. The bar also moves to `bottom: -6 px` and splits into two transitions (`transform` for length, `opacity` for weight), so hover is a 45%-opacity "clickable" hint and only the current section is solid, and `:focus-visible { outline-offset }` stops the keyboard ring from being hidden behind it.

- **对比页与隐私页在 ≤760px 不再失去整条页头导航**：≤760px 那段里的 `.site-nav { display: none }` 与 `.nav-menu { display: block }` 从未限定作用域，而汉堡菜单是两份落地页独有的结构——两条对比页与隐私页因此在小屏上把导航直接隐藏，又没有汉堡可点开，页内锚点（对比页 6 个）与跨页出口（隐私页 3 条）全部点不到，而这一切在桌面宽度上完全看不出来。现在这些规则收在 `.site-header--menu` 之下（对比页补上该 class 与一个真正的汉堡面板），没有汉堡的页面走 `flex-wrap: wrap` 换行兜底。
  **The comparison and privacy pages no longer lose their whole header nav below 760 px.** The `.site-nav { display: none }` and `.nav-menu { display: block }` rules in the ≤760 px block were never scoped, but the hamburger only existed on the two landing pages—so the comparison pages and the privacy policy hid their nav with no menu to open, leaving six in-page anchors and three cross-page links unreachable, none of which is visible at desktop widths. Those rules now live under `.site-header--menu` (the comparison pages gained the class plus a real hamburger panel), and headers without a menu fall back to `flex-wrap: wrap`.

- **落地页轮播不再因一张竖图错位**：`scripts/generate-store-assets.mjs` 生成落地页图时用 `resize(..., { fit: 'inside' })`，等比缩放下竖长的弹窗截图只保证高度 750，实际输出 429×750，其余五张是 1200×750。轮播轨道按每张图的自然宽度排布，于是这一张只有别人三分之一宽、却高出近两倍，横向滚动时基线错位、左右翻页按钮与截图不同高。现在生成脚本先把截图居中合成到 1200×750 的品牌底色画布上再转 JPG，六张落地页图尺寸完全一致（已重跑 `pnpm assets` 并逐张核对）；`landing.css` 另给 `.slide img` 补 `aspect-ratio: 16/10` + `object-fit: contain`，今后即使有人手工塞一张非常规比例的图进 `docs/assets/img/`，轨道也不会再被撑歪。
  **The landing-page carousel stops misaligning because of one tall image.** `scripts/generate-store-assets.mjs` resized landing shots with `fit: 'inside'`, which preserves ratio—so the portrait popup screenshot came out 429×750 while the other five were 1200×750. The gallery lays slides out at their natural width, giving that one slide a third of the width and nearly twice the height, which broke the scroll baseline and left the arrows mismatched with the slides. The generator now composites each shot centered on a 1200×750 branded canvas before encoding, so all six landing images are identical in size (verified by re-running `pnpm assets`); `landing.css` additionally pins `.slide img` to `aspect-ratio: 16/10` with `object-fit: contain`, so a hand-placed off-ratio image can't skew the track again.

- **更正备注关键词 `cxp` 的来历说明**：中英两份落地页与两份 README 都写着 `cxp` 是「工程名 `cross-origin-proxy` 的首字母」，而它的首字母其实是 `cop`。关键词本身不动——已经按 `cxp` 备注加过好友的人要能对上，而 `cop` 在英文里先被读成「警察」——改的是说法：现在写成真实推导 `cross`→cx、`proxy`→p。
  **The stated origin of the `cxp` friend-request keyword was wrong.** Both landing pages and both READMEs called `cxp` the initials of `cross-origin-proxy`, which would be `cop`. The keyword itself stays — people who already applied with `cxp` must still match, and `cop` reads as "police" before it reads as an acronym — what changed is the explanation, which now gives the real derivation: `cross`→cx, `proxy`→p.
- **关闭总开关后网络层规则不再代理请求**：总开关只挡住了后台通道，仅重写 URL 的简单规则仍以 `declarativeNetRequest` 动态规则留在浏览器网络层里继续转发。现在关闭总开关会清空这批动态规则，重新打开时按当前规则集重建。
  Turning the global switch off now actually stops proxying. Rules that only rewrite the URL were still installed as network-layer redirect rules and kept forwarding requests; switching off now clears that rule set, and switching back on rebuilds it from the current rules.
- **「复制规则」不再丢字段**：复制出的新规则会丢掉 HTTP 方法过滤与查询参数注入配置，得到一个和原规则行为不同的副本。现在这两个字段与其余配置一起深拷贝。
  **Duplicating a rule kept its HTTP method filter and query-parameter overrides.** The copy behaved differently from the rule it was made from; both fields are now carried over with the rest of the configuration.
- **首栏里的行内图标不再被拉成整栏宽度**：`docs/assets/landing.css` 里既有的 `.hero-visual svg` 选择器本意是给首栏插图用，却会命中首栏内任意一个行内图标。两个对比页的「一句话版本」框因此把 18×18 的对勾撑到 470 像素宽，正文被挤成一列竖排的单字。现在这条规则收窄到首栏插图所在的 `<figure>`（两个落地页首栏内没有任何 `<svg>`，实测宽度不变），框本身也改用站点约定的「图标 + 单段落」写法。
  **Inline icons in the hero column are no longer stretched.** The pre-existing `.hero-visual svg` rule was written for a hero illustration but matched any inline icon in that column, so the comparison pages' 18×18 check-mark expanded to 470px and squeezed their one-sentence summary into one Chinese character per line. The rule now reads `.hero-visual figure svg` (neither landing page has an `<svg>` in its hero, so its layout is measurably unchanged), and the box uses the site's icon-plus-single-paragraph callout pattern.
- **前缀规则不再拼出坏的重定向地址**：匹配模式以 `/` 结尾时，该斜杠已被模式消耗，剩余路径却直接贴到目标地址后面，`https://fat.com/api/` + 目标 `https://uat.com/v2/` 因此变成 `https://uat.com/v2users`。网络层、后台通道与 WebSocket 三处现在都补回分隔斜杠。
  **Prefix rules stopped building broken redirect URLs.** A pattern ending in `/` consumed that slash, so the remaining path was glued straight onto the target and `https://fat.com/api/users` with target `https://uat.com/v2/` became `https://uat.com/v2users`. The network layer, the background channel and the WebSocket path all restore the separator now.
- **前缀模式里的 `*` 按字面量处理**：网络层曾把它当成正则量词，于是 `https://fat.com/a*b` 会命中 `https://fat.com/aaab` 这类完全不相干的地址并一并转发。现在与后台通道一致，只有字面包含 `a*b` 的地址才命中。**这是一次刻意的收窄**：若你此前依赖 `*` 在前缀模式里当通配用，请改用通配匹配类型。
  **A literal `*` inside a prefix pattern is no longer a wildcard.** The network layer treated it as a regex quantifier, so `https://fat.com/a*b` also matched unrelated URLs like `https://fat.com/aaab` and redirected them. It now agrees with the background channel: only URLs literally containing `a*b` match. **This is a deliberate narrowing** — switch such a rule to the wildcard match type if you relied on the old behaviour.
- **优先级留空不再连带打掉所有网络层规则**：一条规则的优先级缺失或被导入文件写成非数字，会让整批 `declarativeNetRequest` 规则被浏览器拒绝，于是**所有**仅重写 URL 的规则同时停止转发；命中顺序也变得不确定。现在这类值统一回落到默认优先级 10（导入的规则仍按既定的 100 排在后面）。
  **An empty or invalid priority no longer disables every network-layer rule.** One bad value made the browser reject the whole batch of redirect rules, so all URL-rewrite-only rules stopped proxying at once, and rule ordering became indeterminate. Such values now fall back to the default priority of 10 (imported rules keep their deliberately later default of 100).
- **查询参数注入不再改坏其他参数**：注入前原本会重新编解码整个查询串，`?q=a%20b` 变成 `?q=a+b`、`?redirect=https://y.com` 被转义成 `%3A%2F%2F`，依赖原文比对的签名与回调地址白名单因此校验失败。现在只有你指定的参数会被改写，其余保持字节一致（WebSocket 规则同样）。
  **Query-parameter injection stopped re-encoding parameters you never touched.** Injecting one override rewrote the whole query string, turning `?q=a%20b` into `?q=a+b` and escaping `?redirect=https://y.com` into `%3A%2F%2F`, which broke signature checks and callback-URL allowlists that compare raw text. Only the parameters you name are modified now; the rest stay byte-identical, including on WebSocket rules.
- **后台异常不再让请求静默走原生网络**：后台读取配置失败时回的是不带请求标识的异常信封，拦截器认领不到对应请求，页面要挂满 35 秒超时才失败，随后按兜底逻辑**把请求真的发出去**——被阻断的请求也不例外。现在桥接层会补齐信封，失败立即返回，且命中阻断规则的请求在任何异常路径下都绝不回退。
  **A background failure no longer leaks requests to the real network.** When the background could not reply, its malformed envelope carried no request id, so the interceptor could not match it: the page hung for the full 35-second timeout and then fell back to issuing the request natively — including requests a block rule was supposed to stop. The bridge now completes the envelope so failures surface immediately, and a blocked request never falls back, on any error path.
- **生产包保留告警日志，规则里的凭据不再广播给页面**：发布构建此前会剥掉全部 `console` 调用，把「网络层规则被整批拒绝」「正则不是 RE2 兼容所以被跳过」这类只有告警可查的故障一并变成静默。现在只移除 `debugger`。同时，规则中配置的请求头、请求体、响应改写与 Mock 内容在下发给页面前被剥离——它们只有后台用得上，而任何同页面的脚本都能读到跨 world 消息。
  **Production builds keep diagnostic warnings, and rule credentials no longer reach page scripts.** Release builds stripped every `console` call, silencing the only signal for "the browser rejected my whole rule batch" and "this regex is not RE2-compatible, so it was skipped"; only `debugger` is removed now. Separately, header overrides, request/response body overrides and mock content are dropped before the rule set is posted to the page, since only the background needs them and any script on the same page can observe cross-world messages.
- **规则表单不再拒绝保存自己存下的规则**：目标地址留空是合法配置——不改写地址，只让扩展原样转发并注入请求头，但表单把它当必填拦下来。这类规则一旦再次打开就保存不了，只能先随便填一个真实地址。现在只对非空值做格式校验，字段下补一行说明它留空意味着什么，URL 匹配测试也不再因为目标地址为空而禁用。
  **The rule editor no longer refuses a rule it saved itself.** An empty target URL is valid — the request is forwarded unchanged while the extension injects headers — but the form treated it as required, so reopening such a rule made it unsavable unless you invented an address first. Only non-empty values are format-checked now, the field explains what leaving it blank means, and the URL match test no longer disables itself over it.
- **删除后的「撤销」不再在收尾窗口里静默失灵**：提示条的存活时间与延迟提交的定时器同为 5 秒，而离开动画期间它仍然能被点击。在这段重叠里点「撤销」既不会找回规则，也不给任何反馈，删除照常落库。现在提交前先把提示收起，过期之后的点击明确告知「已过期，规则已删除」。
  **Undoing a deletion no longer goes quiet at the deadline.** The toast lived exactly as long as the commit timer, yet stayed clickable through its dismiss animation: clicking Undo inside that overlap restored nothing, said nothing, and the rule was deleted anyway. The toast is now dismissed before the delete is issued, and a late click answers with an explicit expiry notice.
- **被规则挡下的请求终于有痕迹**：规则里的头名非法、请求体超过上限时，页面只拿到一句通用错误，本地日志里连一条记录都没有——用户在自己的日志抽屉里看不到规则被拒过。现在这类请求会留下一条写明原因的记录（只带头名，不带头值），列表与详情都以「失败」标注并展示原因，状态筛选也补了「失败」一档（代理失败不带状态码，数字区间圈不住它）。同时请求体上限改为量最终真正出站内容的 UTF-8 字节数：此前按字符数判定，一段全中文 body 实际体积会被低估到三倍；而**规则注入的 body 此前完全绕过上限，现在一并计量**——若你依赖注入超大 body，请改用导出/导入或直接请求。
  **Requests a rule rejects now leave a trace.** An invalid header name or an oversized body returned one generic error to the page and wrote nothing to the log, so rejections were invisible in your own log drawer. Rejected requests are now logged with a specific reason (the header name, never its value), flagged as failed in both list and detail, and filterable by a new Failed status — a proxy failure carries no status code, so the numeric buckets could never match it. The body cap is also measured in UTF-8 bytes on the payload that actually goes out; it previously counted characters, underestimating CJK bodies by up to three times, and **a body injected by a rule bypassed the cap entirely and is now counted** — reach for import/export or a direct request if you relied on injecting an oversized body.
- **日志详情的响应区块标注到位**：请求与响应的头区块此前同名「请求头」，二进制响应体则显示「暂无数据」，而真实情况是它按既定策略不写盘。现在两处分别标注「请求头」「响应头」，二进制响应体给出明确说明。
  **The log detail labels its response blocks honestly.** Request and response headers both read "Request Headers", and a binary response body showed "no data" when the real answer was that binary bodies are deliberately not stored. The two sections are labelled separately now, and a binary response says so.
- **四处被静默丢弃的样式恢复**：`rgb(var(--cop-primary-rgb, 64, 158, 255), 0.15)` 用逗号接 alpha，而该令牌存的是空格分隔通道（`64 158 255`），拼不出合法的 `rgb()`——整条 `box-shadow` 被浏览器丢掉，空状态引导卡与快速模板卡悬浮时因此没有阴影。另一侧，`--cop-fill-color-light`、`--cop-text-color`、`--cop-font-mono` 三个令牌从未在 `assets/theme/tokens.css` 定义，引用它们同样静默失效：设置弹窗的 `kbd` 键帽没有底色，迁移预览的标题与规则名退回继承色、URL 退回平台通用等宽字体。现改用既有令牌与项目内在用的等宽字体栈，并新增 `tests/designTokens.test.ts`（6 条）盯这三类写法：`--cop-*` 引用必须在令牌层有定义、`-rgb` 通道只能写成 `rgb(var(--x-rgb) / NN%)`、动效降级必须留在令牌层。
  **Four style declarations that were being dropped in silence are back.** `rgb(var(--cop-primary-rgb, 64, 158, 255), 0.15)` passed alpha with a comma while the token stores space-separated channels (`64 158 255`), so no valid `rgb()` could be built and the whole `box-shadow` was discarded — the empty-state guide cards and quick templates had no hover shadow at all. On the other side, `--cop-fill-color-light`, `--cop-text-color` and `--cop-font-mono` were never defined in `tokens.css`, and every declaration using them failed just as quietly: the settings dialog's `kbd` chips rendered with no fill, and the migration preview's titles and rule names fell back to an inherited colour with the platform's generic monospace font. They now reference tokens that exist and the mono stack the project already uses, and a new `tests/designTokens.test.ts` (6 cases) guards the three shapes: every `--cop-*` reference must be defined, a `-rgb` channel may only be used as `rgb(var(--x-rgb) / NN%)`, and the motion degradation must stay in the token layer.

## [1.0.0] - 2026-09-07

首个版本，解决一个具体问题：页面连的是 FAT 环境，要验的东西只在 UAT——在浏览器里加一条规则就完成跨环境联调，不改应用代码，也不请后端放开 CORS。
First release. One problem: your frontend talks to FAT but the change you need only exists on UAT — one browser rule closes the gap, with no application code and no backend CORS change.

### Added

- **规则驱动的请求转发**：按通配符、前缀或正则匹配 URL 并重写到目标环境；仅重写 URL 的规则编译为 `declarativeNetRequest` 网络层重定向（单请求零 JS 开销），其余走后台通道。
  **Rule-based URL rewriting** by wildcard, prefix or regex. Rules that only rewrite the URL compile to `declarativeNetRequest` network-layer redirects (zero per-request JavaScript); everything else runs through the background channel.
- **请求改写**：注入或替换请求头（目标环境 token 等）、替换请求体。
  **Request modification**: inject or replace request headers (e.g. the target environment's token) and replace request bodies.
- **响应改写**：界面可覆盖状态码、响应头，或按点分路径（`data.token`）改写单个 JSON 字段；状态文本与整块响应体的覆盖存在于数据结构并被后台执行，但没有界面入口，只能通过导入的 JSON 配置写入。
  **Response modification**: the rule form overrides the status code, response headers, and individual JSON fields by dot-notation path (`data.token`). Overriding the status text or the whole body is part of the stored schema and is honoured by the proxy, but has no editor, so it only arrives through an imported JSON config.
- **Mock / 延迟 / 阻断 / 重试**：直接返回 JSON / 文本 / HTML / XML；注入 0–60000 ms 延迟验证加载与超时；把请求阻断成网络错误验证兜底；重试按规则开启，默认关闭，开启后在网络错误或 5xx 时追加 1–5 次尝试、间隔 100–30000 毫秒。
  **Mock / delay / block / retry**: return your own JSON / text / HTML / XML; inject 0–60000 ms latency to exercise loading and timeout states; fail requests like a network error to exercise fallbacks; retry is a per-rule switch, off by default, adding 1–5 extra attempts at a 100–30000 ms interval on a network error or a 5xx.
- **条件化 Mock**：按 URL 正则、HTTP 方法、查询参数命中，首个命中的条件决定响应体、状态码与 Content-Type。
  **Conditional mock**: conditions on URL pattern, HTTP method and query parameters; the first match decides body, status and content type.
- **HTTP 方法过滤与查询参数注入**：把规则限定到指定方法，或在代理后的地址上追加 `__env=uat` 之类的灰度标识。
  **Method filter and query-parameter injection**: scope a rule to specific methods, or append gray-release tags to the proxied URL.
- **WebSocket 转发**：`ws://` / `wss://` 按 URL 重写转发，实时功能跟同一套环境切换。
  **WebSocket proxying**: `ws://` / `wss://` handshakes are rewritten by URL, so real-time features follow the same environment switch.
- **规则工作台**：快速模板、复制、撤销删除、拖拽排序、批量启停与删除、带逐条预览的目标域名批量迁移、按名称/状态/匹配类型搜索筛选，以及同模式更高优先级规则的遮蔽冲突提示。
  **Rule workspace**: quick templates, duplicate, undo delete, drag-to-reorder priority, batch enable/disable/delete, batch target-domain migration with per-rule preview, search and filters, plus a shadowing-conflict warning.
- **诊断能力**：URL 匹配测试器（命中规则、重写结果、转发通道、被遮蔽规则）、最近 500 条请求日志（筛选、可调自动刷新、详情视图、复制为 cURL、由日志建规则），以及两条通道各自的命中统计。
  **Diagnostics**: a URL match tester (matched rule, rewritten URL, forwarding channel, shadowed rules), the last 500 log entries with filters, adjustable auto-refresh, a detail view, copy-as-cURL and "create a rule from this entry", plus per-rule hit counts for both channels.
- **导入导出**：JSON 配置（覆盖或合并）、HAR 1.2 导出与导入（由录制流量自动建规则）、cURL 导入（DevTools 复制的命令直接预填规则表单）。
  **Import and export**: JSON configuration (replace or merge), HAR 1.2 export and import that creates rules from recorded traffic, and cURL import that prefills the rule form.
- **环境配置快照**：把整套规则存成命名快照，在 FAT / UAT / PROD 间一键切换。
  **Environment profiles**: save the rule set as a named snapshot and switch between FAT, UAT and PROD in one click.
- **界面与自动化**：弹窗总开关、今日统计、最近请求、自动关闭倒计时（`chrome.alarms`，跨服务工作线程重启持久化）、工具栏角标、当前页命中预览、"为此页面创建规则"；中英双语、6 套主题与浅色/深色/跟随系统、快捷键 `⌘⇧P` / `Ctrl+Shift+P`。
  **Interface**: popup with a global switch, today's stats, recent requests, an auto-off countdown persisted across service-worker restarts, a toolbar badge, a current-page match preview and "create a rule for this page"; English / Chinese UI, six themes, light / dark / system, and a keyboard shortcut to toggle proxying.
- **本地优先**：规则、日志、快照与偏好全部只写入 `chrome.storage.local`；无账号、无统计埋点、无遥测、无自有服务端。
  **Local-first**: rules, logs, profiles and preferences live only in `chrome.storage.local`; no accounts, no analytics, no telemetry, no servers of ours.

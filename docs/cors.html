报 blocked by CORS policy 之后：先分清是哪一种失败，再决定改哪一侧

这句报错是浏览器在同源策略下拒绝把响应交给页面，不是后端崩了——服务端通常已经收到请求、也已经回了。要选解法，先分清三种情况：简单请求缺 Access-Control-Allow-Origin、预检 OPTIONS 没过，或者改写后 Origin 变成了 null。三者的修法互相矛盾，混着试只会更久。

第一步是读报错原文，而不是「跨域了」

浏览器把好几件不同的事报成同一个形状。下表左边那一串是你会在原样复制的控制台里看到的字，右边给出下一步该做什么。

报错原文、更可能的原因与下一步
你看到的 更可能是 下一步
No 'Access-Control-Allow-Origin' header 响应缺这个头，或它的值与页面来源不匹配 看 三种失败 的第一种与 五种解法
Response to preflight request doesn't pass 预检 OPTIONS 没过 看 预检那一笔到底要回什么
net::ERR_FAILED，控制台没有 CORS 文案 连接层失败：DNS、端口、TLS、服务没起 先在终端 curl -v 那个地址，与浏览器无关
status === 0，页面只拿到一个 error 被 CORS 拦、断网、DNS 失败、连接被拒——四种在页面上是同一个形状 看 Network 面板里那一笔有没有响应行；没有就是连接层
401 / 403，但请求确实发出去了 后端拒绝了，不是 CORS 看后端日志与凭据，别在浏览器侧找原因

一条判据把两侧分开：CORS 是浏览器行为，服务端一定收到了请求（预检那一笔也会到）。如果服务端日志里一笔都没有，问题在网络层，不在 CORS——这时候改响应头是白改。

三种失败长得一样，修法相反

先把眼前这一笔归到其中一类，再动手。三类的判据、改法和代价各不同。

① 简单请求缺 ACAO

GET 且没有自定义头，请求直接发出，响应回来后发现没有 Access-Control-Allow-Origin（或值不是这个页面的源）。

改法：让响应带上这个头，或者让请求不由页面发出（见 解法 5）。

② 预检没过

带自定义头、Content-Type: application/json、PUT / DELETE 都会先发一笔 OPTIONS。预检的响应要同时给出方法、头与来源，缺一项就拒。

改法：见 预检那一笔到底要回什么。这一类最常被误判成「接口挂了」。

③ 改写后 Origin 变成 null

用网络层重定向把请求改写到另一个原点时，目标收到的是 Origin: null，不是页面自己的源。按来源白名单放行的后端会拒——而它拒得有道理，那个源确实不是它认识的任何一个。

实测于 Chrome for Testing 155（2026-10-13）；改写后仍落在同一原点内的规则保留真实 Origin。详见 这一类的现场读数。

五种解法，按「改动落在谁身上」排

这张表是本页的核心：同一个报错有五种常见解法，它们的区别不是「方不方便」，而是谁要改、改完影响谁、能不能收回。

五种解法的改动落点、代价与适用场景
解法 改动落在谁身上 代价 什么时候用它
1. 后端补 CORS 响应头 服务端 / 网关，通常要走一次发版 要改部署配置并让安全侧同意放行范围；临时放开最容易收不回来 这就是线上形态的一部分，或长期需要别的来源也调它
2. 本地开发代理 每个项目各一份配置，改动进版本库 逐项目重复；启动期生效，改一次要重启；对已部署的页面无能为力 只有本地一个前端、且后端就在同一台机器上跑
3. 反向代理成同域 部署侧（Nginx / 网关 / 负载均衡） 要动环境；域名与路径规划是团队的公共决策 能改部署，且希望所有前端一次性解决
4. 关掉浏览器安全策略 只有你自己这台机器的一个浏览器实例 整个实例裸奔，且联调结论不可外推——别人正常浏览器里仍然被拦 只想一次性验证「确实是 CORS 卡的」这一个判断
5. 浏览器扩展代发 / 重写 只有浏览器，不改服务端、不改项目文件 只覆盖浏览器内流量；配置存在个人 profile，不会自己跟着项目走——要分享就得导出一份文件交出去 环境是别人的、代码不能动、只想把这一页的接口指到另一台后端

1. 后端补 CORS 响应头——唯一能算「修好了」的那一种

响应需要给出 Access-Control-Allow-Origin（精确来源或 *）、必要时 Access-Control-Allow-Methods 与 Access-Control-Allow-Headers；要带 Cookie 时还必须回显具体来源并给出 Access-Control-Allow-Credentials: true（* 在这一档不算数）。这是唯一让「线上也正常」的解法，其余四种都只解决你此刻这一台浏览器。

复现判据：curl -i -H 'Origin: https://你的前端源' https://接口地址，看回包里有没有那几个头。

2. 本地开发代理——把跨域变成同域，代价是每个项目一份

Vite / webpack 的 devServer.proxy、或前端自己起一个小转发，把 /api 指到后端，浏览器看到的始终是同源地址。它干净、可 review、能进版本库，团队共享一份配置。

两个限制值得先说：它的键是站点内相对路径（/api 这种），请求始终同源，后端环境从不出现在请求 URL 上；以及它只在「页面也是这个本地服务渲染出来的」时成立——你要调的是一个已经部署在 FAT 上的页面时，那份配置管不到它。

3. 反向代理成同域——一次改完，所有人都受益

在 Nginx / 网关上把前端与接口挂在同一个域下（/api 转发到后端），跨域这件事从此不存在。这是几种解法里唯一「做完就不用再想」的，但它要动部署、要排期，而且路径规划是团队级决策，不是个人调试能决定的事。

4. 关掉安全策略——它解决的是观测，不是问题

--disable-web-security 之类的启动参数让浏览器不再做这道校验。看起来最快，代价也最隐蔽：那个窗口里所有站点之间的隔离一起没了；而且你观测到的行为已经不是别人那份行为——你在裸奔窗口里看到「通了」，同事与用户的正常窗口里仍然是拦的，联调结论因此不能外推。它只适合一次性确认「确实是 CORS 卡的」。

5. 浏览器扩展代发 / 重写——不改代码也不改后端时的那一条

本扩展做的就是这件事，而且分两条通道，代价不同：

  • 只做地址重写的规则编译成浏览器网络层的重定向（declarativeNetRequest）：转发由浏览器网络栈完成，扩展不为这一笔代发，也不留逐条请求日志。 说准确一点——页面上的请求包装对每一笔都会跑一遍，只是它手里那份规则表压根不含这条规则，所以它只会把请求原样交回原生实现。它改的是「请求发到哪」，页面那一侧仍是一次跨域请求，所以 第 ③ 类失败在这条通道上照样会发生。
  • 带任何高级能力（改请求头或请求体、改响应、Mock、延迟、阻断、重试、携带 Cookie、方法过滤、查询参数注入，以及长连接规则）的，由扩展后台代发：请求由扩展发出、页面拿到扩展构造的响应，页面这道校验不参与——第 ① ② 两类它直接接得住。第 ③ 类实践中也常改到这条通道上来，但要说清楚：后端此刻收到的请求长什么样，我们至今没有量过（量过的是网络层重定向那一头），所以这一格给的是「值得一试的修法」，不是「必然放行」。

边界要说在前面：它只管浏览器里的流量。手机 App、桌面程序、CI 里的脚本都不经过它；配置存在你个人的浏览器 profile 里，需要分享给同事时走导出 / 导入。完整的取舍在同类方案对比页。

预检那一笔到底要回什么

OPTIONS 只在「非简单请求」时发生：自定义头、Content-Type: application/json、PUT / DELETE 都会触发。它要同时满足三项，缺一项就整笔被拒。

  • Access-Control-Allow-Origin：精确来源或 *
  • Access-Control-Allow-Methods：包含实际使用的那个方法
  • Access-Control-Allow-Headers：包含你实际发出去的那几个头——这一条最常漏，加了鉴权头却只放了 Content-Type

两个坑：① 预检回了 200 但没有那几个头，浏览器照样拒绝——预检的响应头才作数，状态码与正文都不作数。② 带凭据时 * 不算数，必须回显具体来源，并给出 Access-Control-Allow-Credentials: true。

改写之后后端说 Origin 不对

这一条最容易误判，因为它看起来像「代理没生效」，实际是代理生效了、浏览器却不肯把响应交给页面。

2026-10-13 在 Chrome for Testing 155 上实测：一条把请求改写到另一个原点的网络层规则，目标服务收到的是 Origin: null（Sec-Fetch-Site: cross-site），不是页面自己的源；改写后仍落在同一原点内的规则保留真实 Origin。

于是会出现这种组合，三行彼此不打架：

  • 页面：Failed to fetch，Network 里是 net::ERR_FAILED
  • 后端：回了 200，但响应里没有 Access-Control-Allow-Origin
  • 同一后端、同一份凭据直连：200 且头齐全

服务端侧独立对过账：curl -H 'Origin: null' 打过去回 200 但没有回显来源，换成 -H 'Origin: http://localhost:5300' 就回显——这就是「200 但浏览器不给页面读」的形状。

别把它写成一条恒真结论。回 Access-Control-Allow-Origin: * 的后端接得住跨原点改写（实测有过这一格），但 Chrome 的网络服务对跨原点 fetch 还有别的拒绝路径——同一格在三轮探针里出现过 FAIL 与 200 两种读数。所以既不能说「跨原点改写必挂」，也不能说「必不挂」。稳妥的两条路：让后端放行，或者给这条规则加一项头覆盖，让它落到扩展代发那一条通道上。

上面那三行读数不必靠猜。环境响应对比（配置页顶栏，见 能力清单里那一节）把同一份地址、方法、请求头与正文 原样发给两个环境，并排给出状态码与逐行正文——它不匹配规则、不写请求日志，也不进命中统计， 所以读回来的是那两个环境自己怎么说，而不是扩展替它们怎么说。而「这笔到底走没走代理、走的哪条通道」是另一问， 那两问分别由自检与 URL 匹配预演回答。

什么时候浏览器方案也解决不了

这几条不是「还没优化」，是这类工具的形状决定的。碰到它们，请回到解法 1 或 3。

要覆盖非浏览器流量

手机 App、桌面程序、服务端进程发出的请求根本不经过这个浏览器，扩展看不见它们。

配置要能进代码评审

扩展的规则活在你个人的 chrome.storage.local 里。团队共用一份转发关系，正确做法是写进仓库的 devServer 配置或网关配置。

接口本身还不存在

需要先跟后端约定字段形状时，可分享的产物是 API 客户端里那份请求定义，不是浏览器里的一条规则。

长连接上的高级能力

WebSocket 只有三件事生效：握手地址重写、查询参数注入、阻断（把握手送到一个连不通的地址）。改请求头、改请求体、改响应、Mock、延迟、重试与携带 Cookie 在握手上都不生效——这是协议形状，不是待修缺陷。

同步 XHR

open() 第三个参数写成 false 时，响应必须在调用栈返回前就绪，而代发只能在之后把结果送回，所以这类请求只能原样发出——只有一种例外：那条规则是阻断时不回退，因为不回退正是用户要的效果。

超过 10 MB 的正文

请求体与回包各有 10 MB 上限，越界那一笔判失败、不做截断返回——削掉一截 JSON 只是把错误挪进页面的 JSON.parse。但「判失败」不等于「这一笔没出门」：走 fetch 时页面会按「代理失败」回退原生再发一次，所以页面可能照样拿到一份来自原地址的响应，而扩展日志里记的是失败；XHR 不回退，直接以 status 0 报错。只有阻断是真的不发出去。

常见问题

关于扩展自身的 FAQ（能力边界、隐私、权限、两条通道怎么分流）在产品介绍页；这一节只回答「报错之后怎么办」。

服务端日志里能看到请求，页面却说 CORS 被拦，是不是后端的问题？

两件事都成立。CORS 是浏览器行为：请求确实发出去了，服务端也确实回了，是浏览器在把响应交给页面之前按响应头判了一次。所以后端「我这边一切正常」和页面「我被拦了」同时为真， 修的方向是让响应带上浏览器认的那几个头，或者让请求不再由页面自己发起。

预检 OPTIONS 回了 200，为什么还是报错？

因为预检那一笔的响应头才作数，正文与状态码都不作数。回 200 但缺 Access-Control-Allow-Origin，或者 Access-Control-Allow-Headers 没覆盖你实际发出去的那个头，浏览器一样拒绝。带自定义头时最常见的漏法是只放了 Content-Type，忘了你加的那个鉴权头。

关闭浏览器安全策略来绕过 CORS，为什么不算解法？

它把整个浏览器实例的防护一起关掉了：那个窗口里所有站点都能互相读写，而不只是你的接口。更麻烦的是它改变了被观测的行为——你在无防护的窗口里看到「好了」，而同事和用户的窗口里仍然是拦的，联调结论不能外推。真要长期用，代价大于收益，它只适合一次性验证某个判断。

用浏览器扩展代发和开发代理有什么区别？

开发代理改的是「你本地怎么发」：要在每个项目里配一份，配完是构建期或启动期的事，且请求必须走那个本地端口。扩展改的是「浏览器怎么发」：一条规则对这台机器上所有项目、所有页面生效，不用重启服务，也不动项目文件。代价是它只覆盖浏览器里的流量，手机 App、桌面程序与 CI 里的脚本都不经过它。

改写之后后端说 Origin 不对，怎么办？

这是浏览器在网络层完成重定向的结果：把请求改写到另一个原点之后，目标收到的是 Origin: null，而不是页面自己的源（实测于 Chrome for Testing 155；改写后仍落在同一原点内的规则保留真实 Origin）。按来源白名单放行的后端因此拒掉这一笔。回 Access-Control-Allow-Origin: * 的后端接得住这一类改写，但 Chrome 的网络服务还有别的拒绝路径，同一格两次读数不同过，所以既不能当必成，也不能当必败。稳妥的两条路：让后端放行，或者把这条规则改成需要扩展代发的形态（加任一头覆盖即可），由扩展发出这一次请求——后者免掉的是页面那一侧的校验，而目标此刻看到的 Origin 是什么，本机没有量过，所以它是值得一试的修法、不是必然放行。

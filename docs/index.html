Point a FAT frontend at a UAT backend — one rule, no code changes

Cross-Origin Proxy is an open-source Chrome extension (Manifest V3) that redirects the API requests a page makes to another backend environment. Rewrite URLs, headers and responses, mock data, inject latency, block requests and forward WebSocket — all configured in the browser, all stored locally.

The problem it removes

Cross-environment debugging usually costs one of three things: a backend change, a config change in every project, or a fake local build. This extension moves all three into a single browser rule.

Before and after, for the common "the UAT service has the fix, my FAT page does not" case
Without the extension With one rule
Edit the devServer proxy table, then restart the dev server. Add https://fat-api.example.com/* → https://uat-api.example.com. Applies immediately.
Ask the backend to add your origin to Access-Control-Allow-Origin and redeploy. Requests with any advanced capability are answered by the extension, so page CORS checks do not apply.
Hardcode a token for the other environment in the source, and remember to revert it. Inject the header per rule; disable the rule when you are done.
Wait for an API that is still being built, or stub it inside the app. Mock the response in the rule; the app code stays untouched.

How it works: two channels, one rule set

Every enabled rule is classified once, on save. A rule that only rewrites the URL is compiled into a declarativeNetRequest redirect and handled by the browser's network stack — no JavaScript runs per request. Anything richer is routed through the extension's background channel. 

Page fetch / XHR / WebSocket
   |
   +-- simple rule (URL rewrite only) --> declarativeNetRequest redirect
   |                                      resolved in the network layer, zero JS per request
   |
   +-- complex rule --> page interceptor (main world)
                          +-> bridge (isolated world) --> background request
                                                          +-> response handed back to the page

A rule stops being "simple" as soon as it has any of

The exact conditions that switch a rule to the background channel
Capability Why the network layer cannot do it
Request header / body override Body replacement needs a real request to be re-issued.
Response status, header or JSON field override The response has to be read and rebuilt.
Mock, delay, block, retry These change whether and when a request happens at all.
HTTP method filter Redirect rules cannot match on method.
Query parameter injection Applied after rewriting, outside redirect substitution.
WebSocket (ws:// / wss://) Redirect rules have no WebSocket resource type.
Wildcard pattern not ending in *, or empty target Redirect substitution would silently drop trailing text or produce an invalid value.

If the interceptor cannot handle a request, the page falls back to its native fetch, XMLHttpRequest or WebSocket — the request still goes out normally. Block rules are the deliberate exception: a blocked request is never replayed.

Features

Proxy & rewrite

Match by wildcard, prefix or regular expression. Rewrite the URL, inject or replace request headers, replace the request body, override response status, headers and individual JSON fields by dot path.

Mock, delay, block

Return a crafted JSON / text / HTML / XML body without touching a server. Add 0–60000 ms of latency to exercise loading and timeout states. Block a request to test failure handling.

Method & query control

Limit a rule to specific HTTP methods, or append and override query parameters such as __env=uat and gray-release tags without rewriting the whole URL.

WebSocket

Forward ws:// and wss:// connections by URL rewrite, so sockets — not just REST calls — follow the same environment switch.

Rule management

Duplicate, batch enable or disable, drag to reorder priority, search and filter, and batch-migrate target domains with a live change preview when environments rotate.

Logs & debugging

Inspect method, status, duration and matched-rule statistics; open any entry for full headers and body; copy it as cURL or export the capture as HAR 1.2.

Import & profiles

Import a HAR file or paste a cURL command to create rules. Save the current set as a named environment profile and switch between FAT, UAT and PROD in one click.

Interface

English and Chinese UI, six themes with light / dark / system modes, a match preview for the page you have open, and shortcuts: ⌘⇧P toggle, ⌘N new rule, / search, Esc close.

The trade-off is honesty: the extension is browser-scoped. It cannot help a server-to-server call, it does not record anything to a cloud workspace, and its rules live in your Chrome profile rather than in a shared project file — export JSON when you want a teammate to have them.

Install

1. Build

git clone https://github.com/GH_OWNER/cross-origin-proxy
cd cross-origin-proxy
pnpm install
pnpm build

2. Load

Open chrome://extensions, enable Developer mode, click Load unpacked and select .output/chrome-mv3.

3. First rule

  1. Turn the proxy switch on in the popup.
  2. Add a wildcard rule: https://fat-api.example.com/* → https://uat-api.example.com.
  3. Reload the page and check the request log.

Requires Node.js 20 or newer and pnpm to build from source. Development: pnpm dev serves the extension with hot reload on port 8899.

Privacy and permissions

Everything is stored on your machine in chrome.storage.local. There is no account, no analytics, no telemetry and no remote service: the only network traffic is the API traffic you ask it to proxy. Logs and exports are produced locally. Read the privacy policy.

Every permission the manifest declares, and what it is used for
Permission Why it is needed
storage Persist rules, request logs, environment profiles and preferences.
declarativeNetRequest Install the network-layer redirect rules that make simple rewrites cost zero JavaScript.
declarativeNetRequestFeedback Read which redirect rules actually matched, for the hit statistics in the log drawer.
alarms Keep the background worker alive while proxying, and run the auto-off countdown.
<all_urls> host permission Proxying has to work on whatever origin your frontend runs on; the target environment is a developer-controlled internal domain, so it cannot be enumerated in advance.

Frequently asked questions

What does a cross-origin proxy for a browser do?

It intercepts the API requests a page makes and sends them somewhere else. In development that usually means pointing a frontend running against one backend at a different environment, so you can test UAT code from a FAT page without editing the app or redeploying.

Does this bypass CORS restrictions?

For rules that carry any advanced capability, yes: the request is issued by the extension's background context, which holds host permissions, and the page receives a response the extension built — page CORS checks do not apply. A pure URL rewrite is instead compiled into a network-layer redirect, where the browser still validates Access-Control-Allow-Origin on the redirected response. If a target environment does not allow your origin, give the rule any capability (a response header override is the cheapest) and it moves to the background channel.

Does it work on any website?

Content scripts are injected on all http and https pages and rules match on request URL, so internal tools, localhost dev servers and staging domains all work. Chrome blocks extensions on chrome:// pages, the Chrome Web Store and other extension pages.

Is my data sent to a server?

No. Rules, logs, profiles and preferences live in chrome.storage.local. There is no analytics or telemetry, and the extension talks to no service of its own.

How is it different from a devServer proxy or a gateway change?

A devServer proxy needs per-project configuration, only sees requests aimed at the dev server, and stays invisible to teammates. A gateway or CORS change needs a backend release. The extension lives in the browser: one rule covers every project you open, it can rewrite responses and mock data, and the whole rule set exports as JSON for your team.

Why do some rules show a different forwarding channel than I expected?

Because a wildcard pattern that does not end in *, or a rule with an empty target, cannot be expressed as a redirect without changing the result. Those are routed to the background channel on purpose. The URL match tester shows the channel for any URL before you rely on it.

What are the limits?

200 rules, the last 500 log entries, a 10 MB request body ceiling, delays of 0–60000 ms, and mocked status codes clamped to 200–599 so the page can always construct a valid Response.

What happens if the extension fails to handle a request?

The interceptor falls back to the browser's native fetch, XMLHttpRequest or WebSocket, so the page keeps working as if the rule were not there. Block rules are the one exception: a blocked request is never replayed natively.

Can I share rules with my team?

Yes: export the configuration as JSON, export captured traffic as HAR 1.2, or paste a cURL command to create a rule. Environment profiles store a named snapshot of the rule set for one-click switching.

Does it work in Firefox or Edge?

It is built and tested against Chrome (Manifest V3). Edge runs Chromium extensions, so the same build normally works there; Firefox's Manifest V3 support differs around declarativeNetRequest, so it is not a supported target today.

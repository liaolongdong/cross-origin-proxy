After blocked by CORS policy: name the failure first, then pick which side changes

That sentence means the browser refused to hand the response to the page under the same-origin policy. It does not mean the backend broke — the server usually received the request and answered it. Before choosing a fix, sort what you have into three cases: a plain request missing Access-Control-Allow-Origin, an OPTIONS preflight that did not pass, or an Origin that became null after a rewrite. Their fixes contradict each other, so trying them in random order only takes longer.

Read the error text, not the label "CORS"

The browser reports several different problems in one shape. The left column below is what you actually see in a console you copied verbatim; the right column says what to do next.

Error text, the likelier cause, and the next step
What you see More likely Next step
No 'Access-Control-Allow-Origin' header The response has no such header, or its value does not match the page's origin See the first of the three failures and the five fixes
Response to preflight request doesn't pass The OPTIONS preflight did not pass See what a preflight must answer
net::ERR_FAILED, with no CORS sentence in the console A connection-layer failure: DNS, port, TLS, or the service is not running Run curl -v against that address in a terminal — no browser involved
status === 0, the page only gets an error CORS blocked, offline, DNS failure and a refused connection all look like this Check whether that row in the Network panel has a response at all; if not, it is the connection
401 / 403, but the request went out The backend refused it — that is not CORS Read the backend log and the credentials; do not look for a cause in the browser

One test splits the two sides: CORS is a browser behaviour, so the server definitely received the request (a preflight reaches it too). If nothing appears in the server log, the problem is at the connection layer and changing response headers will do nothing.

Three failures that look alike and need opposite fixes

Put the request in front of you into one of these three, then act. Each has its own test, fix and cost.

① A plain request with no ACAO

A GET without custom headers goes straight out; the response comes back and there is no Access-Control-Allow-Origin, or its value is not this page's origin.

Fix: send that header, or stop the page from making the request itself (see fix 5).

② The preflight did not pass

Custom headers, Content-Type: application/json, PUT and DELETE each send an OPTIONS first. That answer has to cover origin, method and headers together; miss one and the whole request is rejected.

Fix: see what a preflight must answer. This class is the one most often misread as "the API is down".

③ Origin became null after a rewrite

When a network-layer redirect sends the request to a different origin, the target receives Origin: null, not the page's own source. A backend allowlisting by origin rejects it — and it is right to, since that source is none of the ones it knows.

Measured on Chrome for Testing 155 (2026-10-13); rewrites that stay inside the same origin keep the real Origin. See the readings for this class.

Five fixes, ordered by whose code changes

This table is the point of the page: one error has five common fixes, and they differ not in convenience but in who has to change, who else is affected, and how easily it can be undone.

1. Backend sends CORS headers — the only fix that is actually "fixed"

The response needs Access-Control-Allow-Origin (the exact origin, or *), plus Access-Control-Allow-Methods and Access-Control-Allow-Headers when a preflight is involved. If the request must carry cookies, the answer has to echo the specific origin and add Access-Control-Allow-Credentials: true — at that setting * does not count. This is the only fix that also makes production work; the other four only address this browser, right now.

How to check: curl -i -H 'Origin: https://your-frontend-origin' https://the-api-address and look for those headers in the response.

2. Local dev-server proxy — turns cross-origin into same-origin, at one config per project

Vite / webpack's devServer.proxy, or a small forwarder you start yourself, maps /api to the backend so the browser only ever sees one origin. It is clean, reviewable, and lives in the repository where the team can share it.

Two limits are worth stating first: its keys are site-relative paths (/api), so requests stay same-origin and the backend environment never appears in the requested URL; and it only applies while the page itself is served by that local process. If the page you need is already deployed on FAT, that config has nothing to say about it.

3. Same-origin reverse proxy — change it once and nobody thinks about it again

Put the frontend and the API under one domain at the Nginx / gateway layer (/api forwarded to the service) and cross-origin stops being a question. Of all five this is the only "done and forget", but it needs the deployment, a schedule, and a path plan that is a team-level decision rather than a debugging preference.

4. Disabling security — it fixes the observation, not the problem

Flags like --disable-web-security make the browser skip the check. This looks fastest and hides its cost best: isolation between every site in that window goes away with it, and what you are observing is no longer what anyone else sees. You get "it works" in an unprotected window while colleagues and users are still blocked in a normal one, so nothing from that session transfers. It is good for exactly one question: "is this really CORS".

5. Extension rewrite or proxy — the one for when neither the code nor the backend can change

That is what this extension does, over two channels with different costs:

  • A rule that only rewrites the URL compiles into a network-layer redirect (declarativeNetRequest): the browser's network stack performs the forwarding, the extension does not send that request and no per-request log is written. To be precise — the page-side wrapper still runs for every request, it simply holds a rule list that does not contain this rule, so it hands the call back to the native implementation untouched. What changes is where the request goes; from the page it is still a cross-origin request, so failure class ③ still happens on this channel.
  • A rule with any advanced capability (header or body overrides, response overrides, mock, delay, block, retry, sending cookies, method filtering, query-parameter injection, or a WebSocket rule) is issued by the extension's background: the request goes out from the extension and the page gets a response the extension built, so the page's own check never runs — that channel takes classes ① and ② directly. Class ③ is usually moved onto this channel too in practice, but say it plainly: what the backend receives in that case has never been measured here (the measurements cover the network-layer redirect), so this row is a fix worth trying, not a guarantee that the other side will accept it.

Its edge stated up front: browser traffic only. Mobile apps, desktop programs and CI scripts never reach it, and the rules live in your personal profile — share them with colleagues through export and import. The full trade-off is on the alternatives page.

What a preflight actually has to answer

OPTIONS only happens for non-simple requests: custom headers, Content-Type: application/json, PUT and DELETE all trigger it. Three things must be true at once, and missing any one rejects the whole request.

  • Access-Control-Allow-Origin: the exact origin, or *
  • Access-Control-Allow-Methods: the method you are actually using
  • Access-Control-Allow-Headers: every header you actually sent — this is the usual miss, allowing Content-Type while the auth header you added is absent

Two traps: (1) a preflight that answers 200 without those headers is still a rejection — the preflight's response headers count, its status code and body do not. (2) With credentials, * does not count: the answer must echo the origin and add Access-Control-Allow-Credentials: true.

After a rewrite the backend says the Origin is wrong

This one gets misread most often, because it looks like "the proxy did nothing" when the proxy worked and the browser refused to hand the response over.

Measured on Chrome for Testing 155, 2026-10-13: a network-layer rule that rewrites the request to a different origin delivers Origin: null to the target (Sec-Fetch-Site: cross-site), not the page's own source. Rewrites that land inside the same origin keep the real Origin.

Which produces a combination where all three lines are true at once:

  • Page: Failed to fetch, and net::ERR_FAILED in the Network panel
  • Backend: answered 200, with no Access-Control-Allow-Origin in the response
  • The same backend and the same credentials, requested directly: 200 with the headers present

Reconciled on the server side separately: curl -H 'Origin: null' returns 200 without echoing the origin, while -H 'Origin: http://localhost:5300' does echo it — that is the shape of "200, but the browser will not let the page read it".

Do not turn this into a universal rule. A backend answering Access-Control-Allow-Origin: * does accept cross-origin rewrites (one measured cell did), but Chrome's network stack has other rejection paths for cross-origin fetches — the same cell returned FAIL in one probe round and 200 in another. So it is neither guaranteed to fail nor guaranteed to pass. Two dependable routes: get the backend to allow it, or add one header override to the rule so it falls onto the extension's own channel.

Those three readings are not guesswork. Compare environments (the options-page header; see that part of the feature list) sends one address, method, header set and body verbatim to two environments and lines up the status codes with a line-by-line body diff — it matches no rule, writes no request log and is not counted in hits, so what comes back is what those two environments actually say, not what the extension says on their behalf. Whether a request went through the proxy at all, and on which channel, is a different question: those two are answered by self-check and the URL matcher.

When a browser-side approach cannot help either

These are not "not yet implemented" — they follow from what the tool is. For these, go back to fix 1 or fix 3.

Traffic outside the browser

Mobile apps, desktop programs and server processes never route through this browser, so the extension cannot see them.

Config that must pass code review

The extension's rules live in your own chrome.storage.local. A forwarding relationship the whole team shares belongs in the repository — a devServer config or a gateway config.

The API does not exist yet

When the shape still has to be agreed with the backend, the shareable artefact is the request definition in an API client, not a browser rule.

Advanced capabilities on a socket

WebSocket gets three things only: handshake URL rewrite, query-parameter injection and blocking (which works by sending the handshake somewhere unreachable). Header and body overrides, response overrides, mock, delay, retry and sending cookies do not apply to a handshake — that is the protocol, not a bug.

Synchronous XHR

When the third argument of open() is false, the result has to be ready before the call stack unwinds, while a proxied answer can only arrive afterwards — so those requests go out as they are. The one exception is a rule that blocks: a blocked request never falls back, because falling back would send exactly what the user asked to stop.

Bodies over 10 MB

Request bodies and responses each have a 10 MB ceiling; past it the request fails and is never truncated — cutting a JSON document in half only moves the error into the page's JSON.parse. But "it failed" is not "it never left": a fetch falls back to the native request on a proxy failure, so the page can still get an answer from the original address while the extension logs that entry as failed. An XMLHttpRequest does not fall back — it errors with status 0. Only blocking truly sends nothing. But "failed" does not mean "never left the machine": a fetch falls back to the native request as a proxy failure, so the page can still receive an answer from the original address while the extension's log records that entry as failed. An XMLHttpRequest does not fall back — it errors with status 0. Only blocking really sends nothing.

Questions

The extension's own FAQ — capability limits, privacy, permissions, how the two channels split — is on the product overview. This section only answers "what do I do after the error".

The backend log shows the request, but the page says CORS blocked it. Is the backend at fault?

Both statements are true. CORS is a browser behaviour: the request was sent, the server answered, and the browser judged the response headers before handing the body to the page. So the backend is fine and the page is blocked at the same time. The fix is either to send the headers the browser expects, or to stop the page from being the one that makes the request.

The OPTIONS preflight returned 200 and it still fails. Why?

Only the preflight's response headers count — its status code and body do not. A 200 without Access-Control-Allow-Origin, or with an Access-Control-Allow-Headers that omits one header you actually sent, is still a rejection. The most common miss with custom headers is allowing Content-Type but not the auth header you added.

Why is disabling browser security not a fix?

It switches off the protection for the whole browser instance: every site in that window can now read every other site's data, not just your API. Worse, it changes the behaviour under observation — you see it working in an unprotected window while colleagues and users still hit the block in a normal one, so the conclusion does not transfer. It is fine for one check — is this really CORS — but it is not a workflow.

How is an extension proxy different from a dev server proxy?

A dev server proxy changes how your local build sends requests: one config per project, applied at build or start time, and requests must go through that local port. An extension changes how the browser sends them: one rule covers every project and every page on that machine, with no restart and no project files touched. The cost is reach — it only sees browser traffic, so mobile apps, desktop programs and CI scripts never pass through it.

After a rewrite the backend rejects the Origin. What now?

That is the browser completing a redirect at the network layer. Once a request is rewritten to a different origin the target receives Origin: null rather than the page's own source (measured on Chrome for Testing 155; rewrites that stay inside the same origin keep the real one), so a backend allowlisting by origin refuses it. A backend answering Access-Control-Allow-Origin: * does take this class of rewrite, but Chrome's network stack has other rejection paths and one cell in that measurement read FAIL in one round and 200 in another, so treat it as neither guaranteed nor doomed. Two dependable routes: have the backend allow it, or give the rule one header override so the extension sends the request itself — the second one drops the check on the page side, and what the target sees as its Origin in that case has never been measured here, so it is a fix worth trying rather than a guarantee.
